Register New User

Creates a user in AuthDB → publishes UserRegisteredEvent → 4 services auto-create records

1
Send POST request to register
POST
Endpoint (via Gateway)
POST http://localhost:5000/api/auth/register
Request JSON body
{ "fullName": "Aaryan Sharma", "email": "aaryan@demo.com", "phoneNumber": "9876543210", "password": "Test@1234" }
Expected Response (201 Created)
{ "message": "User registered successfully", "userId": "a1b2c3d4-...", "email": "aaryan@demo.com" }
2
Verify in AuthDB — user row created
SQL
SQL — POLLY\SQLEXPRESS → AuthDb
SELECT Id, FullName, Email, PhoneNumber, PasswordHash, IsActive, CreatedAt FROM Users WHERE Email = 'aaryan@demo.com';
What to show: PasswordHash starts with $2a$12$ — BCrypt work factor 12. Never plain text!
3
Verify event cascade — 4 services created records automatically
SQL
UserProfileDb — profile auto-created via RabbitMQ event
SELECT * FROM UserProfiles WHERE Email = 'aaryan@demo.com';
WalletDb — wallet auto-created
SELECT Id, UserId, Balance, RowVersion FROM Wallets WHERE UserId = '<paste userId from step 1>';
RewardsDb — points account created
SELECT * FROM RewardAccounts WHERE UserId = '<userId>';
Presenter tip: This shows event-driven architecture in action. Auth published ONE event, 3 other services reacted automatically. Zero direct API calls between them!

Login

Validates credentials → returns JWT access token (60 min) + refresh token (7 days)

1
POST login credentials
POST
POST http://localhost:5000/api/auth/login
{ "email": "aaryan@demo.com", "password": "Test@1234" }
Response (200 OK)
{ "accessToken": "eyJhbGciOiJIUzI1NiIs...", "refreshToken": "d4e5f6a7b8c9...", "expiresIn": 3600, "tokenType": "Bearer" }
Copy the accessToken — you'll need it as Authorization: Bearer <token> for ALL protected APIs below.
2
Verify refresh token stored (hashed) in DB
SQL
SELECT Token, ExpiryDate, IsRevoked, CreatedAt FROM RefreshTokens WHERE UserId = '<userId>' ORDER BY CreatedAt DESC;
Key talking point: Token stored as a hash, not plain text. IsRevoked = 0 (active). On next refresh, this gets set to 1 and a new row is created — that's token rotation.

Refresh Token

Exchanges a valid refresh token for a new access token. Old token is immediately revoked (rotation).

1
POST refresh token
POST
POST http://localhost:5000/api/auth/refresh
{ "refreshToken": "d4e5f6a7b8c9... (from login)" }
Response
{ "accessToken": "eyJhbGciOiJIUzI1NiIs... (NEW token)", "refreshToken": "x9y8z7w6v5u4... (NEW refresh token)", "expiresIn": 3600 }
2
Verify old token revoked in DB
SQL
SELECT Token, IsRevoked, ReplacedByToken FROM RefreshTokens WHERE UserId = '<userId>' ORDER BY CreatedAt DESC;
Show: Old row has IsRevoked = 1, ReplacedByToken points to new row. This is how reuse attacks are detected!

Get Wallet Balance

Returns current wallet balance. Wallet was auto-created on registration.

1
GET wallet balance
GET
GET http://localhost:5000/api/wallet/balance
Headers
Authorization: Bearer <accessToken>
{ "walletId": "w1x2y3z4-...", "userId": "a1b2c3d4-...", "balance": 0.00, "currency": "INR" }
2
Verify in WalletDb
SQL
SELECT Id, UserId, Balance, RowVersion, CreatedAt FROM Wallets WHERE UserId = '<userId>';
RowVersion column: This is EF Core optimistic concurrency. If 2 requests try to update balance simultaneously, one will fail with a conflict — preventing double-spend!

Add Money

Credits money to wallet. Creates a double-entry ledger record (Debit + Credit). Idempotency key prevents duplicate credits.

1
POST add money
POST
POST http://localhost:5000/api/wallet/add-money
{ "amount": 500.00, "idempotencyKey": "addmoney-demo-001", "description": "Demo top-up for presentation" }
{ "transactionId": "t1t2t3t4-...", "newBalance": 500.00, "message": "Money added successfully" }
2
Test idempotency — send SAME request again
POST
Send the exact same JSON again (same idempotencyKey). Balance should still be ₹500 — NOT ₹1000. This is the idempotency guarantee!
{ "transactionId": "t1t2t3t4-... (same ID)", "newBalance": 500.00 }
3
Verify double-entry in LedgerDb
SQL
SELECT TransactionId, EntryType, Amount, Description, CreatedAt FROM LedgerEntries WHERE WalletId = '<walletId>' ORDER BY CreatedAt DESC;
Show 2 rows with same TransactionId: One DEBIT (Amount = 500), one CREDIT (Amount = -500). Sum = 0. This is double-entry bookkeeping — same principle banks use!

Transfer Money

Transfers from your wallet to another user's wallet. Atomic — both debit & credit happen in one DB transaction.

0
Pre-step: Register a second user (receiver)
POST
POST http://localhost:5000/api/auth/register
{ "fullName": "Priya Demo", "email": "priya@demo.com", "password": "Test@1234", "phoneNumber": "9111111111" }
Note the userId of Priya — you'll use it as receiverUserId below.
1
POST transfer (logged in as Aaryan)
POST
POST http://localhost:5000/api/wallet/transfer
{ "receiverUserId": "<Priya's userId>", "amount": 150.00, "idempotencyKey": "transfer-demo-001", "description": "Demo transfer to Priya" }
{ "transactionId": "tx-abc-...", "senderBalance": 350.00, "message": "Transfer successful" }
2
Verify BOTH wallets updated atomically
SQL
SELECT UserId, Balance FROM Wallets WHERE UserId IN ('<Aaryan userId>', '<Priya userId>');
Key point: Aaryan: ₹350, Priya: ₹150. Both changed in ONE atomic DB transaction. If it fails halfway, NEITHER changes — that's atomicity.
3
See 4 ledger entries (2 per wallet)
SQL
SELECT WalletId, EntryType, Amount, TransactionId FROM LedgerEntries WHERE TransactionId = '<transactionId from step 1>';

Admin — All Transactions

1
GET all transactions
GET

Headers
Authorization: Bearer <admin accessToken>

Cross-service SQL view — full picture
SQL
SELECT le.TransactionId, le.EntryType, le.Amount, le.Description, le.CreatedAt, w.UserId FROM LedgerEntries le JOIN Wallets w ON le.WalletId = w.Id ORDER BY le.CreatedAt DESC;

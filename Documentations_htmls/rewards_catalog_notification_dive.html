1 Service Context

Exact Responsibility

Rewards Service owns the loyalty programme. Every time a transaction completes anywhere in the platform, the sender earns points. Points accumulate and automatically unlock tiers. The service is entirely event-driven — it never gets called via HTTP for business logic. It only responds to TransactionCompletedEvent from RabbitMQ.

It is a pure downstream consumer. It produces no events, makes no synchronous calls, and never affects the transaction flow. If Rewards goes down, transactions still work perfectly — the user just doesn't earn points until the service recovers and processes the backlog.

✅ Invariants
  • One RewardsAccount per user — created lazily on first event
  • Points = Floor(Amount / 10) — always integer, never fractional
  • Tier never decreases — only calculated upward
  • Same TransactionId = points awarded only once — idempotency
  • TotalPoints = sum of all PointsTransactions — always consistent
💥 What Breaks If Rewards Goes Down
  • Transactions still process normally — Rewards is downstream only
  • Events queue in RabbitMQ — durable queue holds them until recovery
  • Points delayed, not lost — processed when service restarts
  • Users can still redeem existing points via Catalog Service

📄 RewardsDomainService.cs — Pure Calculation Logic
// Static pure functions — no dependencies, fully testable in isolation
public static class RewardsDomainService
{
    // Points formula: Floor(amount / 10)
    // 100 INR = 10 pts | 500 INR = 50 pts | 999 INR = 99 pts | 1500 INR = 150 pts
    public static int CalculatePoints(decimal amount)
        => (int)Math.Floor(amount / 10m);
    // Math.Floor → always rounds DOWN. 99 INR = 9 points, not 10.
    // Use decimal literal 10m — not float 10.0 (precision)

    // Tier calculation — switch expression
    public static RewardsTier CalculateTier(int totalPoints) => totalPoints switch
    {
        >= 5000 => RewardsTier.Gold,
        >= 1000 => RewardsTier.Silver,
        _        => RewardsTier.Bronze
    };
    // Pattern: single responsibility — this method only calculates, never persists
}
Why static pure functions? Tier and points calculation have no side effects and no dependencies. They're pure math — given the same input, always same output. Static pure functions are the easiest to unit test: no mocking needed. CalculatePoints(500) should always return 50 — one line test, zero setup.
📄 TransactionCompletedConsumer.cs — The Heart of Rewards
public class TransactionCompletedConsumer : BaseConsumer<TransactionCompletedEvent>
{
    protected override string QueueName    => EventQueues.TransactionCompletedRewards;
    protected override string ExchangeName => EventQueues.TransactionExchange;
    protected override string RoutingKey   => "transaction.completed";

    protected override async Task HandleAsync(TransactionCompletedEvent message, CancellationToken ct)
    {
        using var scope = _scopeFactory.CreateScope();
        var repo = scope.ServiceProvider.GetRequiredService<IRewardsRepository>();

        // LAZY ACCOUNT CREATION — account created on first transaction, not on registration
        // Why? UserRegistered event isn't always processed before first transaction
        // This is more resilient — account always exists when needed
        var account = await repo.GetByUserIdAsync(message.SenderUserId);
        if (account is null)
        {
            account = new RewardsAccount { UserId = message.SenderUserId, Email = string.Empty };
            await repo.AddAsync(account);
        }

        // Calculate points — pure function, no side effects
        var points = RewardsDomainService.CalculatePoints(message.Amount);
        if (points <= 0) return;  // micro-transactions under 10 INR earn 0 points → skip

        // Update account state
        account.TotalPoints += points;
        account.Tier         = RewardsDomainService.CalculateTier(account.TotalPoints);
        account.UpdatedAt    = DateTime.UtcNow;

        // Append points history — never updated after insert
        await repo.AddPointsTransactionAsync(new PointsTransaction
        {
            RewardsAccountId = account.Id,
            TransactionId    = message.TransactionId,   // for idempotency check
            Points           = points,
            Description      = $"Earned {points} points for {message.TransactionType} of {message.Amount} {message.Currency}"
        });

        await repo.SaveChangesAsync();
        // BaseConsumer → BasicAck on success, BasicNack(requeue:false) on exception → DLQ
    }
}
Missing idempotency gap: The consumer doesn't check if points were already awarded for this TransactionId before creating the PointsTransaction. If the event is delivered twice, the user earns double points. The fix: if (await repo.ExistsByTransactionIdAsync(message.TransactionId)) return; — check before processing. The TransactionId field exists on PointsTransaction specifically for this check.

4 Interview Q&A — Rewards

Q1: Why is RewardsAccount created lazily in the consumer instead of on UserRegistered? ▼
Resilience. The UserRegistered event could fail to reach Rewards (RabbitMQ down, service restart, queue not yet bound). If the account is only created on UserRegistered, a transaction event arriving before the account exists would fail with "account not found" and the points would be lost.

Lazy creation in the TransactionCompleted consumer means: the account is guaranteed to exist before points are awarded. If it doesn't exist, create it on the spot. This makes the consumer self-healing — it doesn't depend on prior events having been processed correctly. Trade-off: the RewardsAccount won't exist for users who never transact — but that's fine, there's nothing to show them anyway.
Q2: What is the idempotency gap in this service and how would you fix it? ▼
RabbitMQ delivers at-least-once. If a TransactionCompletedEvent is delivered twice (network hiccup, service restart during processing), the consumer runs HandleAsync twice for the same event. Both calls create a PointsTransaction for the same TransactionId — double points.

Fix: Before creating the PointsTransaction, check: if (await repo.ExistsByTransactionIdAsync(message.TransactionId)) return; The TransactionId field on PointsTransaction already exists for this purpose. Additionally, add a unique index on (RewardsAccountId, TransactionId) in the DbContext — this provides DB-level protection as a second line of defence.
Q3: Why use static pure functions for CalculatePoints and CalculateTier? ▼
Business rules like "1 point per 10 INR" and "Gold at 5000 points" are pure calculations — same input always gives same output, no side effects, no database, no external calls. Static pure functions are the right pattern for this: they're easily unit-tested in one line with no mocking, they can't accidentally mutate state, and they make the business rule explicit and visible rather than buried in a service method. If a business analyst asks "how are points calculated?" you can point them directly to one static method.

It listens to TransactionCompletedEvents from RabbitMQ, calculates points using Floor(Amount/10), updates the user's RewardsAccount and tier, and appends an immutable PointsTransaction record. 🎯 2-Minute Deep Dive

The key architectural decision is lazy account creation. Rather than depending on a UserRegistered event, the account is created the first time a transaction event arrives. This makes the consumer self-healing — it works correctly regardless of event ordering.

Points calculation uses static pure functions in RewardsDomainService — Floor(Amount/10) and a switch expression for tier. These are zero-dependency, fully unit testable in one line. Tier is recalculated on every points award and never decreases, even when points are redeemed.

The main gap I'd flag is the missing idempotency check. RabbitMQ guarantees at-least-once delivery, so the same TransactionCompletedEvent could arrive twice. The fix is a TransactionId existence check before inserting, backed by a unique DB index. The infrastructure is already in place — TransactionId is stored on PointsTransaction specifically for this.

1 Service Context

Exact Responsibility

Catalog Service is the redemption marketplace. Admins create catalog items (gift cards, vouchers, cashback offers) with a points price and stock count. Users browse and redeem items by spending their loyalty points. When a redemption succeeds, stock decrements by one.

This is the only service with no RabbitMQ at all — no events consumed, no events published. It's pure synchronous REST. This is correct: redemption is a user-initiated, interactive action that needs an immediate result. The user clicks "Redeem" and waits for a response — async event-driven processing would be wrong here.

✅ Invariants
  • Stock never goes below 0 — checked before decrement
  • Only active items are redeemable — IsActive flag checked
  • Redemption is atomic — stock decrement + redemption record in one save
  • Only Admin can create/deactivate items — role-based access
⚠️ Known Design Gap

Points balance not verified at redemption. The service calls item.PointsRequired but never checks if the user actually has enough available points in their RewardsAccount. This is a real bug — a user with 0 points could redeem a 500-point item.

Fix: Call GET /rewards for the user's available points before allowing redemption, OR implement a cross-service points deduction via a shared contract.

📄 RedemptionService.cs — Redemption Logic
public async Task<Result<RedemptionDto>> RedeemAsync(Guid userId, RedeemRequestDto dto)
{
    var item = await _catalog.GetByIdAsync(dto.CatalogItemId);
    if (item is null)
        return Result<RedemptionDto>.Failure("Catalog item not found.");

    // Guard 1 — item must be active (admin hasn't deactivated it)
    if (!item.IsActive)
        return Result<RedemptionDto>.Failure("Item is no longer available.");

    // Guard 2 — stock must be available
    if (item.Stock <= 0)
        return Result<RedemptionDto>.Failure("Item is out of stock.");

    // NOTE: No points balance check here — known gap (see §1)

    // Decrement stock — EF tracks this as a dirty change
    item.Stock--;
    item.UpdatedAt = DateTime.UtcNow;

    var redemption = new Redemption
    {
        UserId        = userId,
        CatalogItemId = item.Id,
        PointsUsed    = item.PointsRequired,
        Status        = RedemptionStatus.Completed
    };

    await _redemptions.AddAsync(redemption);
    await _redemptions.SaveChangesAsync();
    // Single SaveChangesAsync: stock UPDATE + redemption INSERT — atomic

    return Result<RedemptionDto>.Success(MapToDto(redemption, item.Name));
}

public async Task<Result<IEnumerable<CatalogItemDto>>> GetAllActiveAsync()
    => Result<...>.Success(
        (await _catalog.GetAllActiveAsync()).Select(MapToDto));
Race condition on stock: Two users both read Stock=1. Both pass the Stock <= 0 check. Both call item.Stock--. Stock goes to -1 — one item was sold twice. Fix: add a RowVersion on CatalogItem exactly like Wallet — optimistic concurrency catches the second writer. Or use a SQL UPDATE ... WHERE Stock > 0 approach.

4 Interview Q&A — Catalog

Q1: Why does Catalog have no RabbitMQ at all, while every other service does? ▼
Redemption is a synchronous, user-initiated action. The user clicks "Redeem", expects immediate feedback — "Congrats, you've redeemed Amazon Gift Card" or "Out of stock." Async processing would mean they get a "processing" response and have to poll for the result — terrible UX for a simple operation.

RabbitMQ is for fire-and-forget notifications or decoupled reactions to events. Redemption is neither. The stock decrement must happen atomically with the redemption record — if you split them into events, you'd need a saga pattern to handle failures. Synchronous REST + single DB transaction is simpler, faster, and correct here.
Q2: There's a race condition on stock — two users both see Stock=1 and both redeem. How do you fix it? ▼
Two approaches: (1) Optimistic concurrency — add RowVersion to CatalogItem exactly like Wallet. EF wraps the update with WHERE RowVersion=@original. The second concurrent writer finds RowVersion changed → DbUpdateConcurrencyException → return 400 "Item is out of stock." (2) SQL-level atomic decrement — use a raw SQL UPDATE: UPDATE CatalogItems SET Stock = Stock - 1 WHERE Id = @id AND Stock > 0. Check rows affected — if 0, stock was already gone. The first approach uses the same pattern already in the codebase (Wallet). The second is more explicit but requires raw SQL in EF.
Q3: What's the missing check in RedeemAsync and why does it matter? ▼
There's no verification that the user has enough points to cover the redemption. A user with 0 available points could successfully redeem a 500-point item — their points just go negative or the PointsUsed is recorded but never actually deducted from RewardsAccount.

Fix options: (1) Catalog service calls Rewards service synchronously (GET /rewards/{userId}) before redemption — introduces coupling. (2) Rewards service exposes a RedeemPoints(userId, points) endpoint — Catalog calls it as part of redemption. If it fails, the redemption fails. (3) Move points deduction into an event-driven saga. Option 2 is cleanest — it keeps Rewards as the authoritative source of points balance.

📄 GmailSmtpEmailSender.cs — MailKit Implementation
public class GmailSmtpEmailSender : IEmailSender
{
    private readonly IConfiguration _config;

    public async Task SendAsync(string toEmail, string subject, string htmlBody)
    {
        var message = new MimeMessage();
        message.From.Add(new MailboxAddress(
            _config["Smtp:FromName"],   // "WalletPlatform"
            _config["Smtp:FromEmail"])); // dotnet904training@gmail.com
        message.To.Add(MailboxAddress.Parse(toEmail));
        message.Subject = subject;

        // HTML email body
        message.Body = new TextPart("html") { Text = htmlBody };

        using var client = new SmtpClient();

        // CRITICAL: StartTls on port 587 — NOT SslOnConnect on 465
        // System.Net.Mail fails with Gmail — MailKit's StartTls is required
        await client.ConnectAsync("smtp.gmail.com", 587, SecureSocketOptions.StartTls);

        // Gmail App Password — NOT your account password
        // Generate at: Google Account → Security → 2FA → App Passwords
        await client.AuthenticateAsync(
            _config["Smtp:FromEmail"],
            _config["Smtp:Password"]);  // 16-char App Password, no spaces

        await client.SendAsync(message);
        await client.DisconnectAsync(true);
    }
}
Why MailKit instead of System.Net.Mail? Gmail requires STARTTLS negotiation on port 587. System.Net.Mail's SmtpClient has a EnableSsl flag but it uses SSL from the start (SslOnConnect), not STARTTLS — Gmail rejects this. MailKit's SecureSocketOptions.StartTls correctly upgrades the connection. This was a hard-won lesson in building the platform — this was the specific fix that made real emails work.
📄 NotificationDomainService.cs — Log + Send
public class NotificationDomainService
{
    private readonly IEmailSender _emailSender;
    private readonly INotificationRepository _repo;
    private readonly ILogger<NotificationDomainService> _logger;

    public async Task SendAsync(Guid userId, string email, string subject, string body, NotificationType type)
    {
        var log = new NotificationLog
        {
            UserId  = userId,
            Email   = email,
            Subject = subject,
            Body    = body,
            Type    = type
        };

        try
        {
            await _emailSender.SendAsync(email, subject, body);
            log.IsSuccess = true;
            _logger.LogInformation("Email sent to {Email} — {Subject}", email, subject);
        }
        catch (Exception ex)
        {
            // EMAIL FAILURE IS NOT RE-QUEUED — it's caught here and logged
            // Why? Transient SMTP failures shouldn't block the queue
            // The message is BasicAcked (not Nacked) — we accept delivery, even if email fails
            log.IsSuccess    = false;
            log.ErrorMessage = ex.Message;
            _logger.LogError(ex, "Failed to send email to {Email}", email);
        }
        finally
        {
            // ALWAYS log — regardless of success or failure
            await _repo.AddAsync(log);
            await _repo.SaveChangesAsync();
        }
    }
}
Email failure = BasicAck, not BasicNack. If the SMTP send fails (Gmail rate limit, network issue), the exception is caught, logged, and the RabbitMQ message is still Acked. Why? If we Nacked on SMTP failure, the message would requeue and retry. But if Gmail is rate-limiting, every retry would also fail — infinite loop. Email delivery is best-effort. The notification log records the failure for manual investigation. In production, you'd add retry logic with exponential backoff specifically for transient SMTP errors.

4 Distributed Systems Concerns

Why No REST Endpoints?

Notification Service has no reason to be called directly by any other service or by clients. It is a pure side-effect service — it reacts to things that happened. No service needs to "ask Notification to send an email" via HTTP — it just publishes an event and Notification picks it up.

This keeps Notification completely decoupled. If you want to add SMS later, you add a new consumer implementation without changing any other service. The event contract is the only interface.

Fan-In Pattern

While Ledger's TransactionCompletedEvent is a fan-out (one event → many consumers), Notification is a fan-in — it subscribes to events from multiple different exchanges/services and handles them all in one place.

This centralises all email logic: templates, SMTP config, retry logic, audit logging. The alternative — each service sends its own emails — means 8 copies of GmailSmtpEmailSender and 8 places where the App Password is configured.

What happens if Notification consumes an event but SMTP fails, then the service crashes before SaveChangesAsync? The RabbitMQ message was not Acked (service crashed before returning from HandleAsync). RabbitMQ re-delivers it when the service restarts. HandleAsync runs again — email send is retried. If SMTP succeeds this time, the log is created. If SMTP fails again, the log records the failure and the message is Acked. The user may or may not receive the email, but the platform is self-healing for most cases.

5 Interview Q&A — Notification

Q1: Why does Notification Service have no REST endpoints? Is that a design choice or a gap? ▼
Deliberate design choice. Notification is a pure side-effect service — it reacts to domain events, it doesn't need to be called directly. No service needs to say "please send an email to user X" via HTTP. Instead, services publish events about what happened, and Notification handles the email delivery independently.

This gives complete decoupling: adding a new notification type means adding a new consumer in Notification, not modifying any other service. Adding SMS later means adding an SmsConsumer alongside the email consumers. The event contract is the interface — no HTTP contracts to evolve.
Q2: Why BasicAck on SMTP failure instead of BasicNack with requeue? ▼
Because email delivery is best-effort, and SMTP failures are often persistent (Gmail rate limiting, account issues). If we Nacked with requeue=true on SMTP failure, the message goes back to the queue and is immediately re-delivered. If Gmail is rate-limiting, the retry also fails — infinite loop that floods the queue and the logs.

Instead: catch the exception, log it with IsSuccess=false in NotificationLogs, and Ack the message (accept delivery, mark as processed). The notification log is the fallback — ops can query "all failed notifications" and manually trigger resend. In production, add retry logic with exponential backoff specifically for transient SMTP errors before falling through to this Ack-on-failure behaviour.
Q3: Why must event payloads include the recipient's email address? ▼
Notification Service has no database of users — it doesn't store email addresses. If an event only carried UserId, the Notification consumer would need to call Auth or UserProfile service to resolve UserId → Email. This introduces a synchronous dependency: if Auth is down, notifications fail.

By requiring publishing services to include the email in the event payload, Notification remains completely self-contained. The trade-off: every service that publishes notification-triggering events must know and include the email. This is an API contract between the event publisher and Notification. A schema registry or shared event contracts (Shared.Contracts) enforce this.
Q4: Why MailKit instead of System.Net.Mail for Gmail? ▼
Gmail requires STARTTLS — a connection is first established on port 587 unencrypted, then upgraded to TLS. System.Net.Mail's SmtpClient with EnableSsl=true tries to start with SSL (SslOnConnect), which Gmail rejects with an authentication failure. MailKit explicitly supports STARTTLS via SecureSocketOptions.StartTls on port 587. This is a real implementation-level detail that comes up with Gmail SMTP — we discovered this during development when System.Net.Mail kept failing authentication.

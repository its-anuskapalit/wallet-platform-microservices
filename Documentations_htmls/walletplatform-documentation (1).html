Executive Summary

Strategic overview and platform objectives

WalletPlatform — Aurelian is a full-stack, production-grade fintech platform inspired by Paytm and PhonePe. It implements the complete lifecycle of a digital wallet application: from secure onboarding and KYC compliance to multi-party fund transfers, loyalty reward accrual, voucher redemption, AI-assisted customer support, and administrative fraud controls.

The architecture is built on a domain-driven microservices model where each business capability is owned by a dedicated service with its own database, enforcing strict bounded contexts. Services communicate synchronously over HTTP through an Ocelot API Gateway and asynchronously via RabbitMQ for event-driven side-effects.

Security-First

JWT auth, OTP verification, RBAC, refresh token rotation, and idempotency for all financial operations.

10 Microservices

Auth, UserProfile, Wallet, Ledger, Rewards, Catalog, Notification, Receipts, Admin, Chatbot.

Event-Driven

RabbitMQ message bus for async workflows: notifications, receipts, points accrual, wallet creation.

AI-Powered

FastAPI chatbot with Google Gemini 2.5 Flash for real-time user support and FAQs.

Double-Entry Ledger

Every transaction creates immutable debit/credit ledger entries for complete financial auditability.

Containerised

Docker Compose for local dependencies, GitHub Actions CI for automated build and test pipelines.

Architecture Principles

  • Clean Architecture: Every .NET service is layered as API → Core → Infrastructure.
  • Database-per-Service: Hard ownership boundaries; no cross-service SQL joins.
  • Idempotency: Financial endpoints auto-generate or accept idempotency keys to prevent duplicate processing.
  • Event Sourcing Lite: Ledger entries are immutable append-only records; domain events propagate side effects asynchronously.
  • Self-Healing: Profile and Wallet services use get-or-create patterns as a fallback to RabbitMQ delivery.

UC-01: User Registration with OTP

FieldDetail
ActorsUser, Auth Service, Notification Service
PreconditionsUser has valid email and password; email not already registered
Basic FlowUser submits register form → Auth creates user + issues tokens → UserRegisteredEvent published → Wallet, Profile, Rewards seeded asynchronously → Welcome email sent
Alternate FlowUser may also call send-otp and verify-otp for email/phone verification post-registration
Exception FlowDuplicate email → 400 Bad Request; weak password → 400 validation error
PostconditionsUser record, wallet, profile, and rewards account exist; user holds valid JWT pair

UC-02: Wallet Top-Up

FieldDetail
ActorsUser, Wallet Service, Ledger Service
PreconditionsUser authenticated; wallet exists and not frozen
Basic FlowPOST /gateway/wallet/topup → Wallet Service credits balance → Ledger records TopUp transaction → TransactionCompletedEvent fires → Receipt generated, points awarded
Exception FlowWallet frozen → 400; amount ≤ 0 → validation error
PostconditionsWallet balance increased; receipt available; loyalty points credited

UC-03: Money Transfer

FieldDetail
ActorsUser (sender), User (receiver), Ledger Service, Wallet Service
PreconditionsBoth users have wallets; sender has sufficient balance; not a self-transfer
Basic FlowPOST /gateway/transactions → Ledger validates → Writes debit+credit LedgerEntries → TransactionCompleted → Wallet balances adjusted → Both parties emailed → Receipt generated
Alternate FlowRecipient identified by email via UserProfile lookup, then wallet looked up by userId
Exception FlowInsufficient funds → 400; recipient not found → 404; self-transfer → 400
PostconditionsDouble-entry ledger updated; both wallets reconciled; email sent to both parties

UC-04: KYC Submission & Admin Review

FieldDetail
ActorsUser, Admin, UserProfile Service, Notification Service
PreconditionsUser authenticated; KYC not yet approved
Basic FlowUser POSTs KYC payload → Status set to Pending → Admin reviews at POST /gateway/kyc/review/{id} → Status updated → KYCStatusUpdatedEvent → User emailed decision
Exception FlowInvalid document format → 400; non-admin review attempt → 403 Forbidden
PostconditionsKYC record updated; user notified; profile KYC status reflects decision

UC-05: Reward Redemption

FieldDetail
ActorsUser, Catalog Service, Rewards Service
PreconditionsUser authenticated; sufficient points; item in stock and active
Basic FlowPOST /gateway/redemptions → Catalog validates stock + points → Synchronous call to Rewards to deduct points → Voucher issued → PointsRedeemedEvent published
Exception FlowInsufficient points → 400; out of stock → 400; item inactive → 404
PostconditionsPoints deducted; voucher code issued; redemption record persisted

UC-06: Admin Wallet Freeze

FieldDetail
ActorsAdmin, Wallet Service, Notification Service
PreconditionsCaller has Admin role; target user exists
Basic FlowPOST /gateway/wallet/admin/freeze/{userId} + reason body → Wallet frozen → WalletFrozenEvent published → User emailed
Exception FlowNon-admin caller → 403; wallet already frozen → 400
PostconditionsWallet IsFrozen=true; user cannot top-up or send; user emailed alert

API Reference — Ledger Service

Base URL: http://localhost:5000/gateway/transactions

POST /gateway/transactions Initiate a transaction · JWT

Initiates a Transfer, TopUp, or Payment. Auto-generates idempotency key if not provided. Creates immutable debit+credit ledger entry pair.

Request Body

{
  "toUserId": "uuid",
  "amount": 750.00,
  "type": "Transfer",
  "memo": "Rent for March",
  "idempotencyKey": "optional-client-uuid"

{
  "transactionId": "uuid",
  "status": "Completed",
  "amount": 750.00,
  "type": "Transfer",
  "createdAt": "2026-04-15T10:00:00Z"

Validation Rules

  • Amount must be greater than 0
  • Self-transfers not allowed (fromUserId ≠ toUserId)
  • Memo max 256 characters
  • Type must be: Transfer | TopUp | Payment

Security Best Practices Applied

  • Password Hashing: BCrypt with configurable work factor.
  • Refresh Token Rotation: Each use issues a new token; old one immediately invalidated.
  • CORS Policy: Gateway configured to allow only Angular dev origin (http://localhost:4200) in development.
  • Idempotency: Financial endpoints check stored idempotency keys to prevent duplicate processing on retries.
  • Internal Endpoint Protection: Rewards Service internal endpoints (/api/rewards/deduct) use AllowAnonymous but should be network-isolated in production (not exposed via gateway).
  • Structured Logging: No sensitive data (passwords, tokens) in Serilog structured logs.

Glossary & Appendix

Terms, acronyms, assumptions, and version history

Glossary of Terms

Ocelot
Open-source .NET API Gateway providing routing, load balancing, rate limiting, and authentication middleware.
JWT (JSON Web Token)
Compact, URL-safe token for claims transmission. Used for access token authentication across all services.
Refresh Token
Long-lived token (7 days) used to obtain new access tokens without re-authentication. Rotated on each use.
Idempotency Key
Client-supplied or auto-generated UUID that ensures a financial operation is processed exactly once, even on retries.
Double-Entry Ledger
Accounting method where every transaction creates both a debit entry (sender) and credit entry (receiver), ensuring balance integrity.
KYC (Know Your Customer)
Identity verification process for regulatory compliance. Users submit identity documents reviewed by admins.
RBAC (Role-Based Access Control)
Authorization model where permissions are assigned to roles (User, Admin) rather than individual users.
RabbitMQ
Open-source message broker implementing AMQP. Used for async event-driven communication between microservices.
OTP (One-Time Password)
6-digit time-limited code for email/phone verification. Stored hashed with expiry in OtpEntries table.
Clean Architecture
Layered architecture separating API (controllers/DTOs), Core (domain/interfaces), and Infrastructure (data/external services).
Dead Letter Queue (DLQ)
RabbitMQ queue receiving messages that failed processing after maximum retries. Used for operational inspection.
Bill Split
Feature allowing a user to divide a shared expense among multiple participants, who each pay their share independently.
Serilog
.NET structured logging library used across all services for consistent, queryable log output.
Google Gemini
Google's multimodal large language model. Version gemini-2.5-flash used for the AI chatbot assistant.

Assumptions & Constraints

  • Database-per-service is strictly enforced; no shared database schemas.
  • Default currency is INR (Indian Rupee); multi-currency support is a future phase.
  • Local development targets localhost downstream hosts in Ocelot config. Docker-to-Docker requires a separate config file.
  • Gmail SMTP is the configured email provider; credentials are in appsettings.Development.json (not committed).
  • Cloud deployment (Azure / AWS / GCP) is a planned future phase. Current baseline is local development.
  • Swagger UI works per-service only, not through the Ocelot gateway. Use Postman for gateway-level testing.
  • Internal service endpoints (/api/rewards/deduct) are not gateway-exposed but should be network-restricted in production.

02Problem
Real-World FinTech Challenges
Why distributed money movement is genuinely hard
Core Distributed Problem
₹500 transfer: DEBIT User A → CREDIT User B → RECORD Ledger → NOTIFY → REWARD. In a monolith: one ACID transaction. Distributed: partial failure = ghost money.
Failure Scenarios
DebitWallet() succeeds → network drops → CreditWallet() never called → ₹500 vanishes
Client timeout on POST /transfer → retry → ProcessTransfer() called twice → double debit without idempotency
JWT stolen → replay attack on /wallet/credit → unauthorized balance injection
RabbitMQ consumer crash → NotificationConsumer misses message → user never notified
Monolith vs Microservices
ChallengeMonolithOur Solution
Scale payment spikeFull app redeployScale Wallet only
DB bottleneckShared schema lockDB-per-service
Partial failureRollback or corruptCompensation pattern
Audit trailManual log parsingLedger append-only
Auth changesRedeploy entire appAuth Service isolated
Once you move from monolith to distributed, you lose ACID guarantees. The double-entry ledger and idempotency keys are the engineering response to that loss. Every failure scenario listed here was a real design decision point.

05Security
Authentication & Security — JWT + BCrypt + Rotation
Access token lifecycle, refresh rotation, and token revocation
GenerateAccessToken()
private string GenerateAccessToken(User user) {
  var claims = new[] {
    new Claim(JwtRegisteredClaimNames.Sub,
               user.Id.ToString()),
    new Claim(ClaimTypes.Role, user.Role),
    new Claim(JwtRegisteredClaimNames.Jti,
               Guid.NewGuid().ToString())
  };
  var key = new SymmetricSecurityKey(
    Encoding.UTF8.GetBytes(_config["Jwt:Key"]!));
  var token = new JwtSecurityToken(
    issuer: _issuer, audience: _audience,
    claims: claims,
    expires: DateTime.UtcNow.AddMinutes(60),
    signingCredentials: new(key,
      SecurityAlgorithms.HmacSha256));
  return new JwtSecurityTokenHandler()
    .WriteToken(token);
}

RefreshTokenAsync() — Rotation
var stored = await _repo.GetByHashAsync(refreshToken);
if (stored == null || stored.IsRevoked
    || stored.ExpiresAt < DateTime.UtcNow)
  return Result.Failure("Invalid token");

stored.IsRevoked = true; // revoke immediately
var newToken = GenerateRefreshToken();
await _repo.RevokeAndCreateAsync(stored, newToken);
return Result.Success(new AuthResponse(
  GenerateAccessToken(stored.User), newToken));
Stolen refresh token becomes useless the moment the legitimate user makes their next refresh call. Old token revoked atomically before issuing new pair.
Refresh token rotation is the critical security mechanism here. The IsRevoked flag is set to true inside the same DB transaction that creates the new token. A stolen refresh token can only be replayed once before detection.

BaseConsumer<T> — Shared.EventBus
public abstract class BaseConsumer<TMessage> {
  protected abstract Task
    HandleMessageAsync(TMessage msg);

  public void StartConsuming(string queue) {
    _ch.BasicConsume(queue, autoAck: false,
      consumer: new AsyncEventingBasicConsumer(_ch) {
        ReceivedAsync = async (_, ea) => {
          try {
            var msg = JsonSerializer
              .Deserialize<TMessage>(ea.Body.Span);
            await HandleMessageAsync(msg!);
            _ch.BasicAck(ea.DeliveryTag, false);
          } catch (TransientException) {
            _ch.BasicNack(ea.DeliveryTag, false,
              requeue: true);
          } catch {
            // poison msg -> dead.letter.exchange
            _ch.BasicNack(ea.DeliveryTag, false,
              requeue: false);
          }
        }
      });
  }
}
BaseConsumer<T> handles all RabbitMQ ceremony — deserialization, ACK/NACK, dead-letter routing. Every consumer just overrides HandleMessageAsync. Error handling is consistent across all 8 consumers.

TransferAsync() — Full Flow
public async Task<Result<TransferDto>> TransferAsync(
    TransferRequest req, string idempKey) {

  // 1. Idempotency guard
  if (await _idemp.ExistsAsync(idempKey, "WalletSvc"))
    return await _idemp.GetCachedAsync<TransferDto>(idempKey);

  await using var tx = await _db.BeginTransactionAsync();
  try {
    var sender   = await _db.Wallets.FindAsync(req.SenderId);
    var receiver = await _db.Wallets.FindAsync(req.ReceiverId);

    if (sender!.Balance < req.Amount)
      return Result<TransferDto>.Failure("Insufficient balance");

    sender.Balance   -= req.Amount;
    receiver!.Balance += req.Amount;
    // throws DbUpdateConcurrencyException on RowVersion mismatch
    await _db.SaveChangesAsync();
    await _idemp.StoreAsync(idempKey, result);
    await tx.CommitAsync();
    await _bus.PublishAsync(new WalletTransactionCompletedEvent(...));
    return Result<TransferDto>.Success(result);
  } catch (DbUpdateConcurrencyException) {
    await tx.RollbackAsync();
    return Result<TransferDto>.Failure("Concurrent modification");
  }
}
Notice the event is published AFTER CommitAsync. A DB commit failure rolls back cleanly. A publish failure is handled by the DLQ. RowVersion provides optimistic concurrency — no pessimistic locks, no deadlocks.
08Deep Dive
Ledger Service — Double-Entry Accounting
Every transaction = exactly two entries. Their sum must always equal zero.
Core Invariant
∀ TransactionId: SUM(DEBIT) + SUM(CREDIT) = 0
If violated, money has been created or destroyed — that is always a bug.

Ledger is append-only. No UPDATE or DELETE ever executed. Any balance can be reconstructed by replaying all entries.
The Credit amount is stored as -amount so the SUM invariant holds naturally. The Admin invariant validation query is run on a schedule — any non-zero sum is a data corruption alert that requires immediate investigation.
09Idempotency
Idempotency — Preventing Double-Charges
UUID-keyed check-and-insert with unique constraint and 24h TTL
The Failure Scenario
T+0ms: Client sends POST /wallet/transfer · IdempKey: UUID-123
T+100ms: Server processes debit. Network drops before 200 OK arrives.
Client retries same request. Without idempotency: user debited ₹500 × 2. Lawsuit.
With idempotency: server sees UUID-123 already stored → returns cached 200 OK. Debited once.
IdempotencyKey Entity
public class IdempotencyKey {
  public string   Key          { get; set; }
  public string   ServiceName  { get; set; }
  public string   ResponseJson { get; set; }
  public DateTime ExpiresAt    { get; set; }
    = DateTime.UtcNow.AddHours(24);
}
GetOrExecuteAsync<T>()
public async Task<Result<T>> GetOrExecuteAsync<T>(
    string key, Func<Task<Result<T>>> operation) {

  var existing = await _db.IdempotencyKeys
    .FirstOrDefaultAsync(k => k.Key == key
      && k.ExpiresAt > DateTime.UtcNow);

  if (existing != null)
    return JsonSerializer
      .Deserialize<Result<T>>(existing.ResponseJson)!;

  var result = await operation();
  _db.IdempotencyKeys.Add(new() {
    Key = key,
    ResponseJson = JsonSerializer.Serialize(result)
  });
  await _db.SaveChangesAsync();
  return result;
}
Unique Index — Race Condition Safety
mb.Entity<IdempotencyKey>(e =>
  e.HasIndex(k => k.Key).IsUnique());

// Two concurrent retries: one INSERT wins.
// Second gets DbUpdateException:
catch (DbUpdateException ex)
    when (ex.IsUniqueConstraintViolation())
  return await _idemp.GetCachedAsync<T>(key);
Without the unique index, two concurrent retries could both pass the existence check and both execute. The DB constraint makes check-and-insert atomic.
The unique index on IdempotencyKey.Key is the critical implementation detail. It makes the check-and-insert operation atomic at the database level — the application-level check alone is not sufficient for concurrent requests.
10Failures
Failure Handling — DLQ and Resilience
NACK routing, dead letter exchange, and transient vs persistent errors
Message Lifecycle
PublishAsync() → message arrives with delivery tag
BaseConsumer.HandleMessageAsync() executes
Success → BasicAck(deliveryTag, false) → removed from queue
TransientException → BasicNack(requeue:true) → back to queue head
Persistent failure → BasicNack(requeue:false) → DLQ
Admin monitors DLQ count → operator replays or discards
DLQ Queue Declaration
_ch.QueueDeclare(
  queue: "transaction.completed.queue",
  durable: true, exclusive: false,
  autoDelete: false,
  arguments: new Dictionary<string, object> {
    { "x-dead-letter-exchange",
      "dead.letter.exchange" },
    { "x-message-ttl", 86400000 }
  });
Exception Classification
ExceptionStrategyOutcome
SqlException (timeout)NACK + requeueRetry — transient
HttpRequestExceptionNACK + requeueUpstream transient
JsonExceptionNACK → DLQMalformed, retry useless
BusinessRuleExceptionNACK → DLQLogic error, investigate
OperationCanceledNACK + requeueShutdown in progress
MailKit SMTP (Notification)
// System.Net.Mail fails Gmail auth (deprecated)
using var client = new SmtpClient();
await client.ConnectAsync("smtp.gmail.com",
  587, SecureSocketOptions.StartTls);
await client.AuthenticateAsync(user, appPassword);
await client.SendAsync(message);
await client.DisconnectAsync(true);
Classify exceptions before NACK. A JSON parse failure will fail every retry — DLQ immediately. Retrying poison messages wastes resources and delays good messages behind them.
The DLQ is not just a log — it is a recoverable buffer. Messages in the DLQ are not lost. An operator can inspect the payload, fix the root cause, and replay the message. This is the difference between an incident and a data loss event.

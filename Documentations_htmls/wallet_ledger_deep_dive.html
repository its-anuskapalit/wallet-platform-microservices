1 Service Context

Exact Responsibility

Wallet Service owns one number per user: their current balance. It's the financial state store — the fast-read source of truth for "how much money does this user have right now." It does not record history (that's Ledger), does not issue tokens (that's Auth), and does not verify identity (that's UserProfile).

Think of it as the bank account display — it shows your balance and lets you add or remove money, but it doesn't keep the full transaction history itself.

✅ Invariants Always Maintained
  • Balance never goes negative — explicit check before deduct
  • Same idempotency key = same result — no double top-ups
  • Frozen wallet rejects all balance ops — no exceptions
  • One wallet per user — unique index on UserId
  • RowVersion increments on every write — concurrency safety
💥 What Breaks If Wallet Goes Down
  • Top-up and deduct fail — no money movement possible
  • UserRegistered events queue in RabbitMQ — wallet creation delayed
  • Ledger service calls fail (Ledger needs WalletId to record entries)
  • Auth + UserProfile are completely unaffected

📄 Wallet.cs — The Entity (Most Critical Fields)
public class Wallet : BaseEntity
{
    public Guid         Id        { get; set; }
    public Guid         UserId    { get; set; }    // unique — one wallet per user
    public string       Email     { get; set; } = string.Empty;
    public string       FullName  { get; set; } = string.Empty;
    public decimal      Balance   { get; set; } = 0;   // decimal, NOT float
    public string       Currency  { get; set; } = "INR";
    public WalletStatus Status    { get; set; } = WalletStatus.Active;
    public string?      FreezeReason { get; set; }

    // THE MOST IMPORTANT FIELD FOR CONCURRENCY:
    public byte[]       RowVersion { get; set; } = null!;
    // SQL Server TIMESTAMP — automatically increments on every UPDATE
    // EF Core includes this in WHERE clause: UPDATE ... WHERE RowVersion = @original
    // If two writers read the same RowVersion and both try to update,
    // the second one finds RowVersion has changed → throws DbUpdateConcurrencyException
}
Why decimal, not float? Float/double use binary floating point. 0.1 + 0.2 in float gives 0.30000000000000004. For money, that's a bug. Decimal uses base-10 arithmetic — exact for financial figures. Always use decimal(18,4) for money columns. This is configured in DbContext as .HasColumnType("decimal(18,4)").
📄 IdempotencyKey.cs — Duplicate Prevention Entity
public class IdempotencyKey : BaseEntity
{
    public string   Key       { get; set; } = string.Empty;  // UNIQUE index in DB
    public string   Response  { get; set; } = string.Empty;  // JSON-serialised WalletDto
    public DateTime CreatedAt { get; set; } = DateTime.UtcNow;
    // Note: no ExpiresAt in this implementation — keys accumulate over time
    // Production improvement: add TTL + background cleanup job
}

Why store the full response as JSON? When a duplicate request arrives, you return exactly the same response as the first call — same balance, same data. This is critical for clients: if a payment fails mid-flight, the client retries with the same key. They always get back "this is what happened" — not a new calculation.

📄 WalletService.cs — TopUp + Deduct Logic (Core)
public async Task<Result<WalletDto>> TopUpAsync(Guid userId, TopUpDto dto)
{
    // 1. Business rule validation — amount must be positive
    if (dto.Amount <= 0)
        return Result<WalletDto>.Failure("Amount must be greater than zero.");

    // 2. IDEMPOTENCY CHECK — first thing after validation
    var cached = await _idempotency.GetAsync(dto.IdempotencyKey);
    if (cached is not null)
        return Result<WalletDto>.Success(
            JsonSerializer.Deserialize<WalletDto>(cached.Response)!);
    // If found → return cached response, DO NOT touch the balance again

    // 3. Load wallet
    var wallet = await _wallets.GetByUserIdAsync(userId);
    if (wallet is null) return Result<WalletDto>.Failure("Wallet not found.");
    if (wallet.Status == WalletStatus.Frozen)
        return Result<WalletDto>.Failure("Wallet is frozen.");

    // 4. Mutate balance — EF tracks this change
    wallet.Balance  += dto.Amount;
    wallet.UpdatedAt = DateTime.UtcNow;

    // 5. Build response BEFORE saving (so we cache what we're about to return)
    var response = MapToDto(wallet);

    // 6. Store idempotency record — same key, serialised response
    await _idempotency.AddAsync(new IdempotencyKey {
        Key      = dto.IdempotencyKey,
        Response = JsonSerializer.Serialize(response)
    });

    // 7. Single SaveChangesAsync — wallet UPDATE + idempotency INSERT in one transaction
    await _wallets.SaveChangesAsync();
    // EF Core wraps both in one SQL transaction automatically

    return Result<WalletDto>.Success(response);
}

public async Task<Result<WalletDto>> DeductAsync(Guid userId, DeductDto dto)
{
    // Same pattern as TopUp, with one additional guard:
    if (wallet.Balance < dto.Amount)
        return Result<WalletDto>.Failure("Insufficient balance.");
    wallet.Balance -= dto.Amount;
    // ... rest same as TopUp
}

public async Task<Result<WalletDto>> FreezeAsync(Guid userId, FreezeDto dto)
{
    // No idempotency key needed — freeze is idempotent by nature (already frozen = error)
    if (wallet.Status == WalletStatus.Frozen)
        return Result<WalletDto>.Failure("Wallet is already frozen.");

    wallet.Status      = WalletStatus.Frozen;
    wallet.FreezeReason = dto.Reason;
    await _wallets.SaveChangesAsync();

    // Publish event so Notification sends freeze alert email
    await _publisher.PublishAsync("wallet.exchange", "wallet.frozen",
        new WalletFrozenEvent { UserId = userId, Reason = dto.Reason });

    return Result<WalletDto>.Success(MapToDto(wallet));
}
Race condition between idempotency check and insert: Two concurrent requests with the same key both pass the "GetAsync = null" check simultaneously. Both try to INSERT into IdempotencyKeys. The second insert fails with unique constraint violation. This bubbles up as an unhandled exception → 500. In production, wrap in try-catch for DbUpdateException and return the cached record on collision. This is the idempotency race condition — a common interview question.
📄 WalletDbContext.cs — Schema Configuration
protected override void OnModelCreating(ModelBuilder mb)
{
    mb.Entity<Wallet>(e => {
        // Decimal precision — CRITICAL for money
        e.Property(w => w.Balance)
         .HasColumnType("decimal(18,4)")  // 18 digits total, 4 decimal places
         .IsRequired();

        // RowVersion — enables optimistic concurrency
        // SQL Server creates a TIMESTAMP column that auto-increments on every row update
        e.Property(w => w.RowVersion)
         .IsRowVersion();
        // EF generates: UPDATE Wallets SET Balance=@b WHERE Id=@id AND RowVersion=@rv
        // If RowVersion changed (concurrent update) → 0 rows affected → DbUpdateConcurrencyException

        // One wallet per user — enforced at DB level
        e.HasIndex(w => w.UserId).IsUnique();
    });

    mb.Entity<IdempotencyKey>(e => {
        e.HasIndex(i => i.Key).IsUnique();  // prevents duplicate key inserts at DB level
    });
}

5 Distributed Systems — Idempotency + Concurrency Deep Dive

Optimistic Concurrency with RowVersion
// What SQL Server executes under the hood:
UPDATE Wallets
SET    Balance = @newBalance, RowVersion = <auto-increment>
WHERE  Id = @walletId
AND    RowVersion = @originalVersion   ← THE KEY LINE
-- If RowVersion changed (concurrent writer already updated), 0 rows affected
-- EF Core detects 0 rows → throws DbUpdateConcurrencyException

// Two concurrent top-ups for the same wallet:
Thread A: reads Balance=1000, RowVersion=0x0001
Thread B: reads Balance=1000, RowVersion=0x0001
Thread A: writes Balance=1500, RowVersion becomes 0x0002 → SUCCESS
Thread B: tries to write Balance=1500 WHERE RowVersion=0x0001
          → 0 rows affected → DbUpdateConcurrencyException → retry
// Result: correct. Both top-ups applied, not just one.
// Without RowVersion: both write Balance=1500 → one top-up silently lost (LOST UPDATE bug)
Why optimistic, not pessimistic (SELECT FOR UPDATE)? Pessimistic locking with BEGIN TRAN + UPDLOCK locks the row for the entire operation — other transactions queue up. Under high load this causes deadlocks and poor throughput. Optimistic concurrency lets all transactions proceed in parallel and only conflicts at commit time. For fintech at scale, optimistic is preferred — conflicts are rare, not the norm.
Idempotency Pattern — Why the Response is Cached as JSON
// Network retry scenario:
// 1. Client sends POST /topup { amount: 1000, key: "topup-001" }
// 2. Server processes: balance 500 → 1500, stores idempotency record
// 3. Network drops BEFORE response reaches client
// 4. Client doesn't know if it worked — retries with same key "topup-001"
// 5. Server: GetAsync("topup-001") → found! Returns cached { balance: 1500 }
// 6. Client receives confirmation, sees balance = 1500 ← correct, not 2500

// The cached response is the EXACT response from the first successful execution.
// This means the client always sees a consistent view regardless of retries.

// Alternative (worse): just return "already processed" without the response.
// Client doesn't know the new balance — has to call GET /wallet separately.
// By caching the full response, the retry is transparent to the client.

7 Interview Q&A — Wallet

Q1: What is optimistic concurrency and why use it over database locks? ▼
Optimistic concurrency assumes conflicts are rare and lets all transactions proceed. At commit time, EF Core checks if the RowVersion has changed since the row was loaded. If it has, another transaction modified it — EF throws DbUpdateConcurrencyException and the caller retries. No locks held during processing means no deadlocks, better throughput.

Pessimistic locking (SELECT FOR UPDATE) locks the row immediately on read. Every concurrent transaction queues behind it. Under high load, this causes severe contention. For a wallet service that might process thousands of concurrent top-ups, optimistic concurrency is the right choice — write conflicts are rare in practice.
Q2: How does idempotency prevent double charging? Walk through a network failure scenario. ▼
Client sends POST /topup { amount: 1000, key: "tx-uuid-001" }. Server processes successfully — balance goes 500→1500, idempotency record stored. But the network drops before the response reaches the client. Client doesn't know if it worked, so it retries with the same key.

Server receives the retry. First thing after validation: query IdempotencyKeys WHERE Key = "tx-uuid-001". Found — returns the cached WalletDto showing balance = 1500. Balance is NOT touched again. Client sees balance = 1500, which is correct. Without idempotency, the retry would add another 1000 and show 2500 — a double charge.
Q3: Is there a race condition in your idempotency implementation? How would you fix it? ▼
Yes. Two concurrent requests with the same idempotency key both call GetAsync — both get null, both pass the check, both proceed to insert into IdempotencyKeys. The second INSERT hits the unique constraint and throws DbUpdateException, which surfaces as a 500.

Fix: Wrap the entire flow in a try-catch for DbUpdateException. In the catch block, query GetAsync again — now it will find the record (the first request committed it). Return the cached response. This is the "check-then-act with retry" pattern, using the DB constraint as the final arbiter.
Q4: Why is the WalletFrozenEvent published AFTER SaveChangesAsync, not before? ▼
If you publish to RabbitMQ first and then the DB write fails, you've sent a notification saying "wallet frozen" but the wallet is still Active in the DB. The user gets an email saying their wallet is frozen but it isn't — inconsistent state.

Publishing after the DB commit means the event only fires when the state change is durable. If the publish fails after a successful save, the user's wallet is frozen but they don't get the email — which is far less harmful than the reverse. The Outbox Pattern would solve even this gap.

1 Service Context

Exact Responsibility

If the Wallet Service is the bank account display (current balance), the Ledger Service is the bank statement (complete immutable history of every transaction). Every money movement goes through Ledger. It creates the permanent financial record, enforces double-entry accounting, and fans out events to Rewards, Receipts, and Notification.

In accounting terms: the Wallet is a running total. The Ledger is the journal. You can always reconstruct the Wallet balance by summing all Ledger entries. If they ever disagree — the Ledger is the source of truth.

✅ Invariants That Can Never Break
  • Every transaction has exactly 2 LedgerEntries — one Debit, one Credit
  • SUM(Debits) == SUM(Credits) for every TransactionId
  • LedgerEntries are never updated or deleted — append-only
  • Same idempotency key = same transaction returned
  • Transaction status: Pending → Completed (or Failed) — not reversed by default
💥 What Breaks If Ledger Goes Down
  • No new transactions — the entire payment flow stops
  • Rewards not updated — points not awarded until Ledger recovers
  • Receipts not generated — transaction records lost if not retried
  • Wallet balance still works — Wallet is independent; users can top-up
  • Auth + UserProfile unaffected — identity layer independent

Ledger is the hub of the financial fan-out. One TransactionCompletedEvent triggers Rewards (award points), Receipts (store PDF receipt), and Notification (send email) — all independently, all in parallel. This is the fan-out pattern: one event, many independent consumers.

Why separate ITransactionRepository and ILedgerEntryRepository? Transactions are mutable — their Status changes (Pending → Completed). LedgerEntries are immutable — they are only ever inserted, never updated or deleted. Two different behavioural contracts → two different interfaces. If you put both in one repository, nothing stops a developer from accidentally calling an "Update" on a LedgerEntry.

    public Guid      UserId        { get; set; }

Why no RowVersion on LedgerEntry? LedgerEntries are append-only — they are never updated after INSERT. RowVersion is only needed when concurrent updates to the same row are possible. Since we never update ledger entries, there's no concurrency concern on them. Only the Transaction row (Status change) could theoretically need it, but since that update happens within the same service call that creates the entries, there's no concurrent writer.
📄 TransactionService.cs — The Core Double-Entry Logic
public async Task<Result<TransactionDto>> InitiateTransactionAsync(InitiateTransactionDto dto)
{
    // 1. Validations
    if (dto.Amount <= 0)
        return Result<TransactionDto>.Failure("Amount must be greater than zero.");
    if (dto.SenderWalletId == dto.ReceiverWalletId)
        return Result<TransactionDto>.Failure("Sender and receiver cannot be the same.");

    // 2. IDEMPOTENCY CHECK — returns cached if already processed
    var existing = await _transactions.GetByIdempotencyKeyAsync(dto.IdempotencyKey);
    if (existing is not null)
        return Result<TransactionDto>.Success(MapToDto(existing));

    // 3. Parse transaction type enum from string input
    if (!Enum.TryParse<TransactionType>(dto.Type, out var txType))
        return Result<TransactionDto>.Failure($"Invalid transaction type: {dto.Type}");

    // 4. Create Transaction (Status = Pending)
    var transaction = new Transaction {
        Id               = Guid.NewGuid(),
        SenderWalletId   = dto.SenderWalletId,
        ReceiverWalletId = dto.ReceiverWalletId,
        SenderUserId     = dto.SenderUserId,
        ReceiverUserId   = dto.ReceiverUserId,
        Amount           = dto.Amount,
        Currency         = dto.Currency ?? "INR",
        Type             = txType,
        Status           = TransactionStatus.Pending,
        IdempotencyKey   = dto.IdempotencyKey
    };

    // 5. DOUBLE-ENTRY: Create exactly two LedgerEntries
    var entries = new List<LedgerEntry> {
        new LedgerEntry {
            TransactionId = transaction.Id,
            WalletId      = dto.SenderWalletId,
            UserId        = dto.SenderUserId,
            EntryType     = EntryType.Debit,    // money LEAVING sender
            Amount        = dto.Amount,
            Description   = $"Transfer debit to {dto.ReceiverWalletId}"
        },
        new LedgerEntry {
            TransactionId = transaction.Id,
            WalletId      = dto.ReceiverWalletId,
            UserId        = dto.ReceiverUserId,
            EntryType     = EntryType.Credit,   // money ENTERING receiver
            Amount        = dto.Amount,
            Description   = $"Transfer credit from {dto.SenderWalletId}"
        }
    };

    // 6. Mark transaction complete — status change happens in same save
    transaction.Status = TransactionStatus.Completed;
    transaction.LedgerEntries = entries;

    // 7. ONE atomic save — Transaction INSERT + 2 LedgerEntry INSERTs in one SQL transaction
    await _transactions.AddAsync(transaction);
    await _transactions.SaveChangesAsync();
    // If anything fails here — all three inserts roll back atomically

    // 8. Fan-out event — after commit only
    await _publisher.PublishAsync("transaction.exchange", "transaction.completed",
        new TransactionCompletedEvent {
            TransactionId    = transaction.Id,
            UserId           = dto.SenderUserId,
            Amount           = dto.Amount,
            SenderWalletId   = dto.SenderWalletId,
            ReceiverWalletId = dto.ReceiverWalletId
        });
    // Consumers: Rewards (points), Receipts (PDF), Notification (email)

    return Result<TransactionDto>.Success(MapToDto(transaction));
}
The atomicity guarantee: Transaction INSERT + both LedgerEntry INSERTs happen in ONE SaveChangesAsync() call. EF Core wraps all pending changes in a single SQL transaction. Either all three rows are committed together, or none are. You can never have a Transaction record with no LedgerEntries, or LedgerEntries with no parent Transaction. This is the cornerstone of financial data integrity.
📄 LedgerDbContext.cs — Enforcing Immutability in Schema
protected override void OnModelCreating(ModelBuilder mb)
{
    // Transactions — idempotency key must be unique
    mb.Entity<Transaction>(e => {
        e.HasIndex(t => t.IdempotencyKey).IsUnique();
        e.Property(t => t.Amount).HasColumnType("decimal(18,2)");
        e.Property(t => t.Status).HasConversion<string>();
        e.Property(t => t.Type).HasConversion<string>();
    });

    // LedgerEntries — restrict delete to prevent orphan entries
    mb.Entity<LedgerEntry>(e => {
        e.HasOne<Transaction>()
         .WithMany(t => t.LedgerEntries)
         .HasForeignKey(le => le.TransactionId)
         .OnDelete(DeleteBehavior.Restrict);  // ← CRITICAL
         // Restrict = cannot delete a Transaction if LedgerEntries reference it
         // This enforces immutability at the DB level — no accidental deletes
        e.Property(le => le.Amount).HasColumnType("decimal(18,2)");
        e.Property(le => le.EntryType).HasConversion<string>();
    });
}

Why DeleteBehavior.Restrict on LedgerEntry? If someone tried to delete a Transaction (e.g., by mistake), the database would reject it because LedgerEntries still reference it. This enforces immutability at the database level — not just application level. Even if a developer bypasses the application layer and runs a raw DELETE on Transactions, the DB constraint protects the ledger.

7 Interview Q&A — Ledger

Q1: Explain double-entry accounting and why it's used in fintech systems. ▼
Double-entry accounting means every financial transaction creates exactly two ledger entries — one Debit and one Credit — that always sum to zero. ₹500 from User A to User B creates: Debit ₹500 on UserA's wallet (money leaving) + Credit ₹500 on UserB's wallet (money arriving). Sum = 0.

Why fintech uses it: (1) Auditability — you can reconstruct any account balance by summing all its entries. (2) Error detection — if the sum of any transaction's entries is not zero, money was created or destroyed — that's always a bug. (3) Regulatory compliance — banks and payment processors are legally required to maintain immutable transaction logs. (4) Reconciliation — if your wallet balance disagrees with ledger sum, you have a data integrity problem.
Q2: How does the Ledger ensure atomicity when creating a Transaction + 2 LedgerEntries? ▼
EF Core's change tracker tracks all three objects — the Transaction entity and two LedgerEntry entities. When SaveChangesAsync() is called, EF Core emits all three INSERT statements within a single SQL transaction (it wraps them in BEGIN TRAN / COMMIT automatically). If any INSERT fails, the entire transaction rolls back. You can never end up with a Transaction record and no entries, or entries with no parent Transaction. This atomicity is the cornerstone of the double-entry invariant — it can only be violated if someone manually runs SQL that bypasses EF Core.
Q3: Why are LedgerEntries marked with DeleteBehavior.Restrict? ▼
Restrict means: you cannot delete a Transaction if LedgerEntries reference it. This enforces immutability at the database level, not just the application level. Even if a developer writes raw SQL to delete a Transaction, the FK constraint blocks it because the LedgerEntries still point to it. This is defense in depth — application code says "don't delete", database says "you literally can't delete even if you try." Without this, a well-intentioned "cleanup script" could silently delete financial history.
Q4: Why separate Wallet and Ledger into two services instead of one? ▼
They have fundamentally different access patterns and responsibilities. Wallet: one row per user, read for every balance check, updated on every transaction — optimised for fast single-row lookups with concurrency control. Ledger: thousands of rows per user, append-only inserts, queried for history and audit — optimised for immutable time-series data.

Separation also means independent failure modes. If the Ledger service is slow, wallet balance reads are unaffected. If Wallet is down, historical queries still work. In a monolith, a slow historical query could starve balance reads. Microservice separation provides fault isolation.
Q5: What happens if the TransactionCompletedEvent publish fails after the DB commits? ▼
The Transaction is durably committed to LedgerDb — the financial record exists. But Rewards never awards points, Receipts never generates the PDF, and Notification never sends the email. The system is in a state of partial completion — financially correct but operationally incomplete.

The production fix is the Outbox Pattern: instead of calling PublishAsync directly, write the event payload to an OutboxEvents table within the same SaveChangesAsync call. A separate background HostedService polls the outbox table every few seconds and publishes pending events to RabbitMQ, marking them as published. Even if RabbitMQ was down for an hour, events accumulate in the outbox and are delivered when it recovers.

Ledger Service is the permanent financial record of the platform. 🎯 2-Minute Deep Dive

Ledger and Wallet serve different purposes. Wallet stores the current balance — one row per user, optimised for fast reads and concurrent writes using RowVersion optimistic concurrency. Ledger stores the complete immutable history — every Debit and Credit since account creation. You can reconstruct any wallet balance by summing all its ledger entries. If Wallet balance and Ledger sum ever disagree, the Ledger is the source of truth.

The double-entry invariant is enforced in code: for every transaction, exactly two LedgerEntry rows are created — one Debit for the sender, one Credit for the receiver. Both are added to the Transaction's navigation property and committed in a single SaveChangesAsync — one SQL transaction covering three INSERT statements. Partial state is impossible at the database level.

Idempotency uses a unique index on the IdempotencyKey column in Transactions — the same key always returns the same transaction record. The TransactionCompletedEvent then fans out to three independent consumers: Rewards awards loyalty points, Receipts generates the PDF record, and Notification sends the confirmation email.

The main production gap I'm aware of is the Outbox Pattern. Currently, if the RabbitMQ publish fails after the DB commit, the downstream services never fire. The fix is to write the event to an OutboxEvents table in the same transaction, with a background HostedService guaranteeing delivery.

Diamond Problem — How C# Resolves It

⚠️ The Problem

If C# allowed multiple class inheritance and both parents had the same method, which one would the child get? C# avoids this by allowing only single class inheritance. For interfaces, you resolve it with explicit implementation:

interface IA { void Show(); }
interface IB { void Show(); }

class C : IA, IB
{
    void IA.Show() => Console.WriteLine("IA");
    void IB.Show() => Console.WriteLine("IB");
}

C obj = new C();
((IA)obj).Show(); // "IA"
((IB)obj).Show(); // "IB"

What is the difference between an interface and an abstract class? ▼
An interface defines a pure contract — no state, all public. An abstract class can have fields, constructors, and implementation. Use an interface when defining a capability (IDisposable, IRepository); use abstract class when sharing code across related types (BaseConsumer<T> in WalletPlatform). Key: a class can implement multiple interfaces but only inherit one abstract class.
Can you override static methods in C#? ▼
No. Static methods are bound at compile-time based on the declared type, not the runtime type. They don't participate in the vtable. You can use the new keyword to hide a static method, but that's not overriding — calling via base class reference still calls the base version.
Explain the diamond problem and how C# handles it. ▼
If two parent classes define the same method and a child inherits both, which method runs? C# avoids this by allowing only single class inheritance. For interfaces, if two interfaces have the same method signature, the implementing class must explicitly implement each one: void IA.Show() and void IB.Show() separately.
What is the difference between compile-time and runtime polymorphism? ▼
Compile-time: overloading — resolved by the compiler based on parameter types. Runtime: overriding — resolved by the CLR via the vtable at runtime. virtual/override enables runtime polymorphism. Example: WalletPlatform has multiple Transfer() overloads (compile-time), and each Consumer overrides Process() (runtime).

SOLID Principles Architecture

S — Single Responsibility Principle

A class should have only one reason to change. In WalletPlatform, 🏦 Auth Service is a pure event producer — it only handles authentication. It publishes UserRegisteredEvent and makes zero synchronous outbound calls. UserProfile creation, Wallet creation, Notification sending — all handled by separate dedicated services.

// ✅ SRP: AuthService ONLY handles auth
public class AuthService : IAuthService
{

    {
        // 1. Validate, 2. Hash password, 3. Save user, 4. Publish event
        await _publisher.PublishAsync(new UserRegisteredEvent { UserId = user.Id });
        // That's it. No wallet creation, no email sending here.
        return Result<TokenResponse>.Success(tokens);
    }
}
O — Open/Closed Principle

Open for extension, closed for modification. 🔌 BaseConsumer<T> is never modified — you add new consumers by creating new classes.

// Closed for modification — never touch this
public abstract class BaseConsumer<T>
{
    public async Task ConsumeAsync(string json)
    {
        var msg = JsonSerializer.Deserialize<T>(json);
        try { await ProcessAsync(msg); _channel.BasicAck(...); }
        catch { _channel.BasicNack(..., requeue: true); }
    }
    protected abstract Task ProcessAsync(T message);
}

// Open for extension — add new consumers freely
public class RewardsRegistrationConsumer : BaseConsumer<UserRegisteredEvent>

L — Liskov Substitution Principle

Subtypes must be substitutable for their base type without breaking behaviour. ✅ Result<T> extends Result — anywhere a Result is expected, Result<T> works fine.

// Classic LSP violation — Square is NOT a substitutable Rectangle
class Rectangle { public virtual int Width { get; set; } public virtual int Height { get; set; } }
class Square : Rectangle
{
    public override int Width { set { base.Width = base.Height = value; } }
}
// SetWidth(5) also changes height → breaks Rectangle contract

// ✅ WalletPlatform: Result<T> extends Result without breaking contract
public class Result<T> : Result
{
    public T? Data { get; init; }
    public static Result<T> Success(T data) => new() { IsSuccess = true, Data = data };
}

What is SRP and how does WalletPlatform follow it? ▼
SRP says a class has one reason to change. Auth Service is a pure event producer — it authenticates users and publishes UserRegisteredEvent. It does NOT create wallets, profiles, or send emails. Each of those is handled by a dedicated service consuming the event.
Explain OCP with a real example. ▼
BaseConsumer<T> is closed for modification — its ack/nack error handling is never touched. It's open for extension — whenever we need a new consumer (RewardsConsumer, NotificationConsumer), we create a new subclass and override ProcessAsync(). No existing code changes.
What is the classic LSP violation example? ▼
Square extending Rectangle. Setting Width on a Square also sets Height to keep it square — but a Rectangle consumer expects Width and Height to be independent. This breaks the contract. LSP says you should be able to replace a Rectangle with a Square everywhere without surprises.
What is DIP and how is it different from DI? ▼
DIP is the principle: depend on abstractions, not concretions. Dependency Injection (DI) is the mechanism that implements DIP — the runtime injects the concrete implementation through the constructor. WalletService depends on IWalletRepository (DIP). ASP.NET Core's DI container injects SqlWalletRepository at runtime (DI).
Why should interfaces be segregated? ▼
If you have a fat interface with 10 methods, every implementation must implement all 10 — even if it only needs 2. This creates unnecessary coupling. Segregated interfaces mean each class only depends on the methods it actually uses, making testing and refactoring easier.

What is deferred execution in LINQ? ▼
The LINQ query is defined but not executed until you iterate or call a terminal operator (ToList, Count, First). This means you can build up a query step by step and it only hits the database once. Modifying the query after definition but before execution (e.g., adding .Take(10)) is valid.
IEnumerable vs IQueryable — when does it matter? ▼
IQueryable translates your LINQ to SQL (via EF Core expression trees). The filtering happens at the database — efficient. IEnumerable runs the query in C# memory — it loads all rows first. In production with a million transactions, using AsEnumerable() before Where() could OOM your server.
Write a LINQ query to find all duplicate elements in a list. ▼
var dupes = list.GroupBy(x => x).Where(g => g.Count() > 1).Select(g => g.Key); — GroupBy groups identical elements, Where filters groups with more than one occurrence, Select returns just the key (the value).
What is SelectMany used for? ▼
SelectMany flattens nested collections. If each User has a List<Transaction>, and you want a flat list of all transactions: users.SelectMany(u => u.Transactions). It's like doing a flatMap in other languages.

Access Token

60 minutes. Short-lived. Stateless — verified by signature, no DB lookup. Contains: UserId, Email, Roles.

Refresh Token

7 days. Single-use. Stored in DB with IsRevoked flag + ReplacedByToken audit field. Rotated on every use.

// Refresh token rotation in WalletPlatform
public async Task<Result<TokenResponse>> RefreshAsync(string refreshToken)
{
    var stored = await _repo.GetRefreshTokenAsync(refreshToken);
    if (stored == null || stored.IsRevoked || stored.ExpiresAt < DateTime.UtcNow)
        return Result<TokenResponse>.Failure("Invalid token");

    stored.IsRevoked = true;      // Revoke old token immediately
    var newToken = GenerateRefreshToken();
    stored.ReplacedByToken = newToken.Token; // Audit trail
    await _repo.SaveAsync(stored, newToken);

    return Result<TokenResponse>.Success(new() {
        AccessToken = GenerateJwt(stored.UserId),
        RefreshToken = newToken.Token
    });
}
What is middleware and what order should it be in? ▼
Middleware are components in the request pipeline — each can process a request and call the next component. Order: Exception handler first (wraps everything), then HTTPS redirect, then Authentication (who are you?), then Authorization (what can you do?), then routing/controllers. Getting this order wrong causes bugs — e.g., AuthZ before AuthN means you can't check if someone is authorized.
What is the captive dependency problem? ▼
If you inject a Scoped service (like DbContext) into a Singleton service, the Singleton captures and holds that Scoped instance for its entire lifetime. This means the DbContext is never disposed, leading to stale data and connection leaks. Fix: use IServiceScopeFactory inside the Singleton and create a new scope per operation.
Use vs Run vs Map middleware — what's the difference? ▼
Use: has access to next() — can choose to call next or short-circuit. Run: terminal — never calls next(). Map: branches the pipeline based on URL path — useful for health checks or different sub-apps.
How does refresh token rotation work in WalletPlatform? ▼
On each refresh: 1) Validate old token — check DB, not revoked, not expired. 2) Immediately mark old token IsRevoked=true. 3) Generate new token, store ReplacedByToken=new.Token for audit. 4) Return new access + refresh tokens. Single-use: if someone steals a refresh token, it can only be used once before it's revoked.

ControllerBase vs Controller — what's the difference? ▼
ControllerBase is for APIs — no view support, lighter weight. Controller inherits from ControllerBase but adds view-related helpers (View(), PartialView(), etc.) for MVC. For REST APIs, always use ControllerBase.
What is the N+1 problem? ▼
If you load 100 wallets and then access wallet.Transactions for each, EF Core fires 1 query for wallets + 100 queries for transactions = 101 queries. Fix: .Include(w => w.Transactions) — EF Core generates a JOIN and loads everything in 1 query.
What does AsNoTracking() do? ▼
EF Core normally tracks all loaded entities in the ChangeTracker so it knows what changed on SaveChanges. AsNoTracking() disables this — faster for read-only queries since no tracking overhead. Use it on all GET/report endpoints.
Code First vs Database First? ▼
Code First: you write C# entities and EF generates migrations + SQL schema. Used in WalletPlatform — full control over schema. Database First: existing DB schema generates C# entities via scaffolding (dotnet ef dbcontext scaffold). Used when the DB already exists.

WHERE vs HAVING — what's the difference? ▼
WHERE filters rows BEFORE grouping — it operates on individual rows. HAVING filters groups AFTER GROUP BY — it operates on aggregated results. You can't use aggregate functions (SUM, COUNT) in WHERE; use HAVING for those.
RANK vs DENSE_RANK vs ROW_NUMBER? ▼
ROW_NUMBER: always unique 1,2,3,4. RANK: ties get same rank, next rank skips (1,1,3). DENSE_RANK: ties get same rank, next rank doesn't skip (1,1,2). For "second highest salary" use DENSE_RANK — RANK would skip rank 2 if there's a tie at rank 1.
What is a clustered vs non-clustered index? ▼
Clustered: physically reorders table data — only one per table (usually primary key). Non-clustered: separate structure pointing to rows — multiple allowed. WalletPlatform has a unique non-clustered index on IdempotencyKey to ensure exactly-once processing.
Explain double-entry accounting in WalletPlatform. ▼
Every transaction creates exactly two ledger entries: one Debit (positive amount) for the sender, one Credit (negative amount, stored as -amount) for the receiver. This ensures the books always balance — sum of all ledger entries = 0. It's the same principle used by real banks.

What causes a deadlock with async/await? ▼
Calling .Result or .Wait() on a Task in ASP.NET (which has a SynchronizationContext). The continuation tries to resume on the captured context thread, but that thread is blocked waiting for the Task to complete → circular wait → deadlock. Solution: always await. What is the difference between Task.WhenAll and Task.WhenAny? ▼
WhenAll: waits for ALL tasks to complete. If any fails, it throws after all complete. WhenAny: returns as soon as any ONE task completes. Useful for timeout patterns: race your real work against a Task.Delay and if Delay wins, cancel.
throw vs throw ex — why does it matter? ▼
throw (bare) rethrows the current exception, preserving the original stack trace. throw ex sets the stack trace starting point to the current line — you lose the original location where the error occurred, making debugging much harder. Always use bare throw in catch blocks.
What is ConcurrentDictionary used for? ▼
Thread-safe key-value store. Use for in-memory caches shared across concurrent requests. Regular Dictionary is not thread-safe — concurrent reads/writes cause race conditions. ConcurrentDictionary uses fine-grained locking internally. WalletPlatform could use it for the idempotency cache layer.

⚡ Idempotency in SAGA

Every SAGA step must be idempotent — if a message is replayed, it should produce the same result. WalletPlatform uses GetOrExecuteAsync<T>() with a unique DB index on the saga step ID + operation type.

What is the SAGA pattern and why is it used in microservices? ▼
SAGA manages distributed transactions across multiple services without a global database lock. Each service performs a local transaction and publishes an event. If any step fails, compensating transactions roll back previous steps. Used because distributed systems can't use ACID transactions across service boundaries.
Choreography vs Orchestration — when would you use each? ▼
Choreography: services react to events, no central controller. Simple, decoupled, but hard to track overall flow. WalletPlatform registration uses choreography. Orchestration: a saga orchestrator drives the flow, tracks state, and sends commands. More complex but better for long-running multi-step flows with complex compensation logic. Use orchestration when you need visibility into the overall saga state.
What are compensating transactions? Can they always be exact? ▼
Compensating transactions reverse the effect of a previous step. They must be idempotent. Some can be exact (refunding money is exact). Others are approximate — if a welcome email was sent and the saga fails, you can't "unsend" the email, but you can send a cancellation email. This is an accepted trade-off in eventual consistency.
SAGA vs 2PC — which would you choose? ▼
SAGA for microservices — no locks, high availability, eventual consistency. 2PC (Two-Phase Commit) for tightly coupled systems needing strong consistency — but it has a coordinator as single point of failure and holds locks during the prepare phase, reducing throughput. In practice, SAGA with idempotent steps + compensations is the industry standard for microservices.

public class InMemoryCache<TKey, TValue> where TKey : notnull
{
    private readonly ConcurrentDictionary<TKey, (TValue Value, DateTime Expiry)> _cache = new();

    public void Set(TKey key, TValue value, TimeSpan ttl)
        => _cache[key] = (value, DateTime.UtcNow.Add(ttl));

    public bool TryGet(TKey key, out TValue? value)
    {
        if (_cache.TryGetValue(key, out var entry) && entry.Expiry > DateTime.UtcNow)
        {
            value = entry.Value;
            return true;
        }
        value = default;
        return false;
    }

    public void Invalidate(TKey key) => _cache.TryRemove(key, out _);
}

public async Task<List<Transaction>> GetTransactionsAsync(Guid walletId)
{
    var results = new List<Transaction>();

    // using ensures connection is disposed (closed) after block

            Amount    = reader.GetDecimal(1),
            CreatedAt = reader.GetDateTime(2)
        });
    }
    return results;
}

💡 When Would You Choose ADO.NET?

High-performance bulk operations (millions of rows), complex queries that EF Core can't translate efficiently, legacy codebases, or when you need SqlBulkCopy for fast batch inserts. In WalletPlatform, EF Core handles everything — but knowing ADO.NET shows depth.

What are the core ADO.NET classes and what does each do? ▼
SqlConnection: opens a connection to SQL Server. SqlCommand: executes SQL text or stored procs — ExecuteReader (rows), ExecuteNonQuery (INSERT/UPDATE/DELETE returns rows affected), ExecuteScalar (single value). SqlDataReader: forward-only cursor, reads row by row, keeps connection open. SqlParameter: safe parameterized values — prevents SQL injection. SqlTransaction: wraps multiple commands in a DB transaction.
Why must you always use parameterized queries? ▼
SQL Injection. If you concatenate user input into SQL strings: "SELECT * FROM Users WHERE Email = '" + email + "'" — an attacker can input ' OR 1=1 -- and bypass authentication. SqlParameter.AddWithValue() treats the value as data, not SQL code. Always use parameters, never string concatenation with user input.
SqlDataReader vs SqlDataAdapter — when would you use each? ▼
SqlDataReader: forward-only, connected cursor. Best for large result sets where you process rows one by one — low memory. SqlDataAdapter + DataSet/DataTable: loads everything into memory, disconnected. Useful for offline editing, data binding to grids, or when you need to navigate back and forth through results. In modern ASP.NET Core APIs, SqlDataReader is preferred for its lower footprint.
How does ADO.NET compare to Dapper? ▼
Dapper is a micro-ORM built on top of ADO.NET. It handles mapping query results to objects automatically (no manual reader.GetGuid(0)) while keeping raw SQL performance. It's the middle ground between pure ADO.NET (verbose) and EF Core (full ORM). For complex reporting queries in WalletPlatform, Dapper would be a good addition to complement EF Core.

JWT Deep Dive Security

JWT = Header.Payload.Signature

A JWT (JSON Web Token) is a compact, URL-safe token split into 3 Base64Url-encoded parts separated by dots. It is signed but NOT encrypted — anyone can decode the payload.

Header (alg + typ)
{
  "alg": "HS256",   // HMAC SHA-256
  "typ": "JWT"
}
Payload (Claims)
{
  "sub": "user-guid-here",
  "email": "aaryan@mail.com",
  "role": "User",
  "iat": 1714000000,  // issued at
  "exp": 1714003600   // expires (60 min)
}
Signature — The Trust Part

HMACSHA256(Base64(header) + "." + Base64(payload), secretKey)

The signature ensures the token hasn't been tampered with. If any bit of the payload changes, the signature won't match. The server verifies the signature on every request — no DB lookup needed for access tokens.

// Generating token — WalletPlatform AuthService
private string GenerateAccessToken(User user)
{
    var claims = new[]
    {
        new Claim(JwtRegisteredClaimNames.Sub,   user.Id.ToString()),
        new Claim(JwtRegisteredClaimNames.Email, user.Email),
        new Claim(ClaimTypes.Role,                user.Role.ToString()),
        new Claim(JwtRegisteredClaimNames.Jti,   Guid.NewGuid().ToString()) // unique token id
    };

    var key  = new SymmetricSecurityKey(Encoding.UTF8.GetBytes(_config["Jwt:Key"]!));
    var cred = new SigningCredentials(key, SecurityAlgorithms.HmacSha256);

    var token = new JwtSecurityToken(
        issuer:   _config["Jwt:Issuer"],
        audience: _config["Jwt:Audience"],
        claims:   claims,
        expires:  DateTime.UtcNow.AddMinutes(60),
        signingCredentials: cred);

    return new JwtSecurityTokenHandler().WriteToken(token);
}

⚠️ HS256 vs RS256

HS256 — symmetric: same secret key used to sign AND verify. Simple, fast. Risk: any service with the key can issue tokens. WalletPlatform uses this since Auth Service is the sole issuer. RS256 — asymmetric: private key signs (Auth only), public key verifies (all services). Better for multi-issuer setups.

Why Refresh Tokens?

Access tokens are short-lived (60 min) and stateless — they can't be revoked before expiry. A refresh token lets the user stay logged in without re-entering credentials, while being revocable. WalletPlatform stores refresh tokens in DB with full rotation — every use generates a new token and revokes the old one.

public class RefreshToken
{
    public Guid     Id             { get; set; }
    public string   Token          { get; set; } // Cryptographically random
    public Guid     UserId         { get; set; }
    public bool     IsRevoked      { get; set; } // Revoked on use or logout
    public string?  ReplacedByToken { get; set; } // Audit: what replaced this token
    public DateTime ExpiresAt       { get; set; } // 7 days
    public DateTime CreatedAt       { get; set; }
}

// Generating a cryptographically secure refresh token
private string GenerateRefreshToken()
{
    var bytes = new byte[64];
    RandomNumberGenerator.Fill(bytes);
    return Convert.ToBase64String(bytes);
}
🔐 Refresh Token Theft Detection

If an attacker steals a refresh token and uses it, but so does the legitimate user — the second use detects that a revoked token was presented. WalletPlatform should revoke all tokens for that user (force re-login) upon detecting a revoked token use. This is the "refresh token reuse detection" security pattern.

✅ Do
  • Use HTTPS — JWTs sent in plaintext are readable
  • Short access token lifetime (15–60 min)
  • Store refresh tokens in HttpOnly cookies or secure DB
  • Validate iss, aud, exp, signature on every request
  • Use cryptographically secure random for refresh tokens
  • Rotate refresh tokens on every use
  • Revoke ALL tokens on password change
❌ Don't
  • Store sensitive data (passwords, card numbers) in JWT payload — it's Base64, not encrypted
  • Use none algorithm — allows unsigned tokens
  • Use long-lived access tokens (hours/days)
  • Store JWT in localStorage — vulnerable to XSS
  • Ignore clock skew — causes valid tokens to fail
  • Use a weak or short secret key (min 256-bit for HS256)
What are the three parts of a JWT and what's in each? ▼
Header: algorithm (HS256/RS256) + type (JWT), Base64Url encoded. Payload: claims — sub (user ID), email, roles, iat (issued at), exp (expiry), jti (unique token ID). Signature: HMAC or RSA signature of header.payload using the secret key. Critical: the payload is only Base64 encoded, not encrypted — never put secrets in it.
How does the Ocelot gateway validate JWT without hitting Auth Service? ▼
The gateway shares the same JWT secret key and validation parameters. On each request, Ocelot's JWT bearer middleware verifies the signature, checks issuer/audience match, and confirms the token isn't expired — all in-memory, no network call to Auth Service. This is the stateless nature of JWT: trust is established through cryptography, not a database lookup.
Can you revoke a JWT access token before it expires? ▼
Not without a server-side store. JWTs are stateless — if the signature is valid and not expired, it's accepted. To enable revocation you'd need a token blacklist (Redis set of revoked JTI values checked on each request). This adds latency but enables instant revocation. WalletPlatform avoids this complexity by keeping access tokens short-lived (60 min) — revoke via refresh token instead.
What is ClockSkew in JWT validation? ▼
ClockSkew is a tolerance window added to expiry validation to account for clock drift between servers. Default in .NET is 5 minutes — a token that "expired" up to 5 minutes ago is still accepted. WalletPlatform sets it to 30 seconds (tighter), since all services run on the same Windows machine. In distributed cloud deployments, use NTP sync and keep skew small.
HS256 vs RS256 — which would you choose for a multi-service architecture? ▼
RS256 for multi-service. With HS256, every service that validates tokens needs the secret key — if any service is compromised, the attacker can mint tokens. RS256 uses a private key (only Auth Service holds it) to sign, and a public key (all services can have it) to verify. Compromising a downstream service doesn't let an attacker create tokens.

RabbitMQ Messaging

What is RabbitMQ?

RabbitMQ is a message broker — it decouples producers and consumers. A producer publishes a message to an Exchange. The exchange routes it to one or more Queues based on routing rules. Consumers listen on queues and process messages.

Key Terms
  • Producer — publishes messages (Auth Service)
  • Exchange — routing hub (user.exchange)
  • Queue — buffer per consumer service
  • Consumer — processes messages (Wallet, Notification, etc.)
  • Binding — links exchange → queue (with routing key)
  • Ack/Nack — consumer confirms or rejects a message
WalletPlatform Flow
  • Auth publishes UserRegisteredEvent → user.exchange
  • Exchange fans out to 4 queues simultaneously
  • Queue 1: UserProfile.queue → UserProfile Service
  • Queue 2: Wallet.queue → Wallet Service
  • Queue 3: Notification.queue → Notification Service
  • Queue 4: Rewards.queue → Rewards Service

public class RabbitMqPublisher : IEventPublisher
{
    private readonly IConnection _connection;

    public async Task PublishAsync<T>(string exchange, T message)
    {
        using var channel = await _connection.CreateChannelAsync();

        // Declare exchange (idempotent — safe to call multiple times)
        await channel.ExchangeDeclareAsync(
            exchange: exchange,
            type:     ExchangeType.Fanout,
            durable:  true);    // Survives RabbitMQ restart

        var body = JsonSerializer.SerializeToUtf8Bytes(message);
        var props = new BasicProperties
        {
            Persistent   = true,       // Message survives broker restart
            ContentType  = "application/json",
            MessageId    = Guid.NewGuid().ToString()
        };

        await channel.BasicPublishAsync(
            exchange:   exchange,
            routingKey: "",  // Fanout ignores routing key
            body:       body,
            basicProperties: props);
    }
}
// BaseConsumer<T> — WalletPlatform's reusable consumer base
public abstract class BaseConsumer<T> : BackgroundService
{
    private readonly IConnection _connection;
    protected abstract string QueueName { get; }
    protected abstract string ExchangeName { get; }

    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        using var channel = await _connection.CreateChannelAsync();

        await channel.ExchangeDeclareAsync(ExchangeName, ExchangeType.Fanout, durable: true);
        await channel.QueueDeclareAsync(QueueName, durable: true, exclusive: false, autoDelete: false);
        await channel.QueueBindAsync(QueueName, ExchangeName, routingKey: "");

        // Prefetch = 1: don't deliver next message until current is acked
        await channel.BasicQosAsync(prefetchSize: 0, prefetchCount: 1, global: false);

        var consumer = new AsyncEventingBasicConsumer(channel);
        consumer.ReceivedAsync += async (_, ea) =>
        {
            try
            {
                var message = JsonSerializer.Deserialize<T>(ea.Body.Span)!;
                await ProcessAsync(message, ct);
                await channel.BasicAckAsync(ea.DeliveryTag, multiple: false); // ✅ Success
            }
            catch (Exception ex) when (IsTransient(ex))
            {
                await channel.BasicNackAsync(ea.DeliveryTag, multiple: false, requeue: true); // retry
            }
            catch
            {
                await channel.BasicNackAsync(ea.DeliveryTag, multiple: false, requeue: false); // dead letter
            }
        };

        await channel.BasicConsumeAsync(QueueName, autoAck: false, consumer);
        await Task.Delay(Timeout.Infinite, ct);
    }

    protected abstract Task ProcessAsync(T message, CancellationToken ct);
}
⚡ autoAck: false — Why It Matters

With autoAck: true, RabbitMQ removes the message from the queue as soon as it's delivered — before you process it. If your service crashes mid-process, the message is lost. With autoAck: false, you manually call BasicAck after successful processing. Message stays in queue until you explicitly acknowledge it.

Dead Letter Queue (DLQ)

Messages that fail repeatedly (BasicNack with requeue:false) are routed to a DLQ instead of being dropped. Allows inspection, alerting, and manual replay of failed messages.

What is RabbitMQ and why use it instead of direct service calls? ▼
RabbitMQ is a message broker that decouples services. Instead of Auth Service calling 4 downstream services synchronously (tight coupling, cascading failures), it publishes one event. Each service consumes independently. Benefits: Auth doesn't wait for Wallet/Notification to respond, services can be down and catch up when restarted, and adding a new consumer requires zero changes to Auth Service.
Explain the 4 exchange types and when you'd use each. ▼
Direct: routes to queue with exact routing key match — use for task queues or point-to-point. Fanout: broadcasts to ALL bound queues — use for pub/sub (WalletPlatform registration). Topic: pattern matching with * and # wildcards — use for categorized events (payment.*, *.failed). Headers: routes based on message headers — complex routing, rarely used in practice.
What is the difference between BasicAck and BasicNack(requeue:true) vs BasicNack(requeue:false)? ▼
BasicAck: message processed successfully — remove from queue. BasicNack(requeue:true): processing failed but is likely retryable (transient error like DB connection timeout) — put message back in queue for retry. BasicNack(requeue:false): permanent failure — send to Dead Letter Queue if configured. Critical: if you always requeue:true on failure, a poison message will loop forever and block your queue.
What is prefetchCount and why set it to 1? ▼
prefetchCount controls how many unacknowledged messages a consumer receives at once. Setting it to 1 means: don't deliver a new message until the current one is acknowledged. This ensures fair dispatch in multi-instance scenarios and prevents memory overload from buffering too many messages. In WalletPlatform where operations touch the DB, 1 is safe. For high-throughput lightweight tasks, a higher prefetch (e.g., 10–50) improves throughput.
How would you handle message ordering guarantees in RabbitMQ? ▼
RabbitMQ delivers messages in order WITHIN a single queue and single consumer. With multiple consumers or requeue-on-failure, ordering breaks. For strict ordering: 1) Single consumer per queue. 2) Include a sequence number in messages and reorder at the consumer. 3) Use exclusive queues. In WalletPlatform, ledger entries are timestamped and idempotent — exact ordering isn't critical as long as all events eventually arrive.

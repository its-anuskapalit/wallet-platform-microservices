1 Service Context

Exact Responsibility

Receipts Service is the financial paper trail. Every completed transaction gets a permanent receipt record stored here, created automatically by consuming TransactionCompletedEvent. Users can query their transaction history and export it as CSV — the digital equivalent of a bank statement.

Like Rewards, it is a pure downstream consumer — transactions still complete perfectly if Receipts goes down. The events queue in RabbitMQ and process in a burst when the service recovers.

✅ Invariants
  • One receipt per transaction — idempotency check on TransactionId
  • Receipts never deleted or updated — permanent record
  • Both sender and receiver see the receipt — queried by userId (either side)
  • CSV export always reflects full history — ordered by date desc
vs. Ledger — What's the Difference?

Ledger Service owns the accounting entries — double-entry Debit/Credit records for financial correctness.

Receipts Service owns the user-facing transaction record — a single row per transaction that both sender and receiver can query for their statement history.

Ledger = accounting. Receipts = customer statement. Both are derived from the same TransactionCompletedEvent.

📄 Receipt.cs — One Table, Flat Schema
public class Receipt : BaseEntity
{
    public Guid     Id               { get; set; }
    public Guid     TransactionId    { get; set; }   // unique — one receipt per transaction
    public Guid     SenderUserId     { get; set; }   // used for querying sender's history
    public Guid     ReceiverUserId   { get; set; }   // used for querying receiver's history
    public Guid     SenderWalletId   { get; set; }
    public Guid     ReceiverWalletId { get; set; }
    public decimal  Amount           { get; set; }
    public string   Currency         { get; set; } = "INR";
    public string   TransactionType  { get; set; } = string.Empty;  // "Transfer", "TopUp"
    public DateTime TransactionDate  { get; set; }
    // No double-entry here — that's Ledger's job
    // No status field — receipts are only created for COMPLETED transactions
}

Why is there no Status on Receipt? Receipts are only created from TransactionCompletedEvent — the event is only published when the transaction succeeds. A receipt existing means the transaction completed. There's no "pending receipt" or "failed receipt" concept. Failed transactions never produce receipts.

Why store both SenderUserId and ReceiverUserId? The GetByUserIdAsync query returns receipts where the user is EITHER the sender OR receiver — it's their full statement. Without both IDs on the row, you'd need a JOIN or two separate queries. Flat denormalised schema trades storage for query simplicity.
📄 TransactionCompletedConsumer.cs — Receipts Side
public class TransactionCompletedConsumer : BaseConsumer<TransactionCompletedEvent>
{
    protected override string QueueName    => EventQueues.TransactionCompletedReceipts;
    protected override string ExchangeName => EventQueues.TransactionExchange;
    protected override string RoutingKey   => "transaction.completed";
    // Different queue name from Rewards consumer — same exchange/routing key
    // RabbitMQ fan-out: same event delivered to BOTH queues simultaneously

    protected override async Task HandleAsync(TransactionCompletedEvent message, CancellationToken ct)
    {
        using var scope = _scopeFactory.CreateScope();
        var repo = scope.ServiceProvider.GetRequiredService<IReceiptRepository>();

        // IDEMPOTENCY CHECK — receipt already exists for this transaction?
        if (await repo.ExistsByTransactionIdAsync(message.TransactionId))
            return;  // at-least-once delivery handled

        await repo.AddAsync(new Receipt
        {
            TransactionId    = message.TransactionId,
            SenderUserId     = message.SenderUserId,
            ReceiverUserId   = message.ReceiverUserId,
            SenderWalletId   = message.SenderWalletId,
            ReceiverWalletId = message.ReceiverWalletId,
            Amount           = message.Amount,
            Currency         = message.Currency ?? "INR",
            TransactionType  = message.TransactionType ?? "Transfer",
            TransactionDate  = message.Timestamp ?? DateTime.UtcNow
        });

        await repo.SaveChangesAsync();
    }
}
Receipts HAS idempotency — Rewards doesn't. This consumer correctly checks ExistsByTransactionIdAsync before inserting. Contrast with the Rewards consumer which is missing this check. This is the correct pattern — if TransactionCompletedEvent is delivered twice, only one receipt is created. The unique index on TransactionId in DbContext is the DB-level second guard.
📄 ReceiptService.cs — Including CSV Export
public async Task<Result<byte[]>> ExportCsvAsync(Guid userId)
{
    var receipts = await _receipts.GetByUserIdAsync(userId);

    var sb = new StringBuilder();
    // CSV header row
    sb.AppendLine("TransactionId,Amount,Currency,Type,Date");

    // CSV data rows — one per receipt
    foreach (var r in receipts)
        sb.AppendLine(
            $"{r.TransactionId}," +
            $"{r.Amount}," +
            $"{r.Currency}," +
            $"{r.TransactionType}," +
            $"{r.TransactionDate:yyyy-MM-dd HH:mm:ss}");

    // Convert string → UTF-8 bytes for file download
    return Result<byte[]>.Success(Encoding.UTF8.GetBytes(sb.ToString()));
}

// Repository query — sender OR receiver, ordered newest first
public async Task<IEnumerable<Receipt>> GetByUserIdAsync(Guid userId)
    => await _db.Receipts
        .Where(r => r.SenderUserId == userId || r.ReceiverUserId == userId)
        .OrderByDescending(r => r.TransactionDate)
        .AsNoTracking()  // read-only — no change tracking needed
        .ToListAsync();

Why return byte[] instead of a string? The controller sets Content-Type: text/csv and Content-Disposition: attachment, returning a file download. The service layer returns raw bytes — it doesn't know or care that this will be a file download. The controller handles the HTTP concern of making it downloadable.

3 Distributed Systems + Edge Cases

Same Event, Two Consumers — Fan-Out

Ledger publishes TransactionCompletedEvent to transaction.exchange. Both Receipts and Rewards (and Notification) subscribe to the same exchange + routing key but different queues:

  • transaction.completed.receipts.queue
  • transaction.completed.rewards.queue
  • transaction.completed.notification.queue

RabbitMQ delivers one copy to each queue independently. Receipts consumer processes its copy; Rewards processes its copy. Fully decoupled — failure in Rewards doesn't affect Receipts.

4 Interview Q&A — Receipts

Q1: How is Receipts Service different from Ledger Service if both store transaction data? ▼
Ledger owns the financial accounting record — double-entry Debit and Credit entries that must mathematically balance. It's for financial integrity and auditing. Receipts owns the user-facing statement — a single flat row per transaction that users can query and export. Ledger entries are not directly consumable by end users. Receipts are designed for readability: "you sent ₹500 to wallet X on date Y." They serve different consumers: Ledger serves the accounting/audit function; Receipts serve the user-facing product.
Q2: Why does the receipt record store SenderUserId AND ReceiverUserId? ▼
The GetByUserId query returns receipts where the user is either the sender OR the receiver — it's their complete transaction history. Without both IDs on the row, a WHERE clause would need to JOIN another table to find which transactions involved a particular user. The denormalised flat schema with both IDs means one simple WHERE with an OR condition: WHERE SenderUserId = ? OR ReceiverUserId = ?. Storage cost is minimal compared to the query simplicity gained.
Q3: If the service is down for 2 hours, what happens to the receipts for transactions that occurred during that time? ▼
RabbitMQ queues are declared as durable — they persist to disk. Messages accumulate in the queue while the service is down. When Receipts Service restarts, the consumer starts processing from where it left off. All 2 hours of transaction events are processed in a burst. The idempotency check ensures no duplicates. The user's transaction history will be complete and correct after recovery — they'll just have a temporary gap in their receipts view during the outage window.

5 30s + 2min Pitch

⚡ 30-Second

Receipts Service consumes TransactionCompletedEvents and stores one flat receipt row per transaction. Both sender and receiver IDs are stored so either party can query their full history. Idempotency is handled correctly — ExistsByTransactionIdAsync prevents duplicate receipts from at-least-once delivery. Three endpoints: get by transaction, get mine (full history), export CSV. The CSV export returns bytes with Content-Type text/csv and Content-Disposition attachment for browser download.

🎯 2-Minute Deep Dive

The key design decision is schema denormalisation. By storing both SenderUserId and ReceiverUserId on the receipt, a single WHERE OR query returns a user's complete transaction history — no joins needed. This is a read-optimisation trade-off: slightly more storage, significantly simpler queries.

The consumer correctly implements idempotency — unlike the Rewards consumer. Before inserting, it checks ExistsByTransactionIdAsync. The unique index on TransactionId provides a DB-level second guard against the race condition where two concurrent consumer instances receive the same event.

The fan-out pattern means the same TransactionCompletedEvent simultaneously creates a receipt in ReceiptsDb, awards points in RewardsDb, and triggers an email via Notification — all independently and in parallel. If Receipts is slow, it doesn't slow down Rewards or Notification. The services are fully decoupled through the queue.

1 Service Context

Exact Responsibility

Admin Service is the operations control panel. It is the only service where every single endpoint requires Role = "Admin". It owns one domain: fraud flags — the ability for admins to mark suspicious transactions for investigation. It also provides a dashboard summary of platform-wide statistics.

It is deliberately the leanest service in the platform. No RabbitMQ, no complex business logic, no cross-service calls in the core implementation. Just direct DB operations and JWT-role enforcement.

✅ Invariants
  • ALL endpoints require Admin role — no User-accessible endpoints
  • Each transaction can only be flagged once — duplicate guard
  • FlaggedByUserId always from JWT — audit trail, not from request body
  • IsResolved defaults false — flags require explicit resolution
🎯 Design Choice — Why So Minimal?

The original design included controllers for listing all users and all KYC requests — but these were intentionally removed. Those queries would require cross-service calls (Admin → Auth, Admin → UserProfile) creating coupling.

The decision: Admin can access those directly through the Auth and UserProfile services. Admin Service owns what only Admin owns — fraud investigation tooling. Clean separation, no unnecessary coupling.

Why is FlaggedByUserId important? Audit trail — in a regulated fintech platform, every admin action must be traceable to a specific admin user. If a transaction is flagged incorrectly (or fraudulently by a rogue admin), you need to know who did it. This field is always populated from the JWT claim, never from the request body.

        ApprovedKyc           = 0,  // populated 0 — would need HTTP call to UserProfile
        TotalTransactions     = 0,  // populated 0 — would need HTTP call to Ledger
        TotalTransactionAmount = 0, // populated 0 — would need HTTP call to Ledger
        FraudFlags            = fraudFlags,
        UnresolvedFraudFlags  = unresolvedFlags
    });

public async Task<Result<FraudFlagResponseDto>> FlagTransactionAsync(
    Guid transactionId, FraudFlagDto dto, Guid flaggedBy)
{
    // Idempotency — one flag per transaction
    var existing = await _adminRepo.GetFraudFlagByTransactionIdAsync(transactionId);
    if (existing is not null)
        return Result<FraudFlagResponseDto>.Failure("Transaction already flagged.");

    var flag = new FraudFlag
    {
        TransactionId   = transactionId,
        FlaggedByUserId = flaggedBy,   // ← from JWT, never from dto
        Reason          = dto.Reason,
        IsResolved      = false
    };

    await _adminRepo.AddFraudFlagAsync(flag);
    await _adminRepo.SaveChangesAsync();

    return Result<FraudFlagResponseDto>.Success(MapToDto(flag));
}

public async Task<Result<IEnumerable<FraudFlagResponseDto>>> GetFraudFlagsAsync()
{
    var flags = await _adminRepo.GetAllFraudFlagsAsync();
    return Result<IEnumerable<FraudFlagResponseDto>>.Success(flags.Select(MapToDto));
}
Dashboard gap — cross-service data: TotalUsers, TotalTransactions, etc. are all hardcoded to 0 because fetching them requires calling Auth/Ledger/UserProfile services. The correct production implementation uses either: (1) HttpClient calls to each service with the admin's forwarded JWT, or (2) a read model/materialized view maintained by events. For a portfolio project, the honest answer is "this is a known gap I'd address with typed HttpClient factories and IHttpClientFactory."

4 Interview Q&A — Admin

Q1: Why is the dashboard showing 0 for most stats? Is this a bug or a design choice? ▼
It's an honest known gap, not a bug. Populating TotalUsers, TotalTransactions etc. requires Admin Service to call Auth, Ledger, and UserProfile services via HTTP. This is cross-service synchronous coupling — and for a dashboard that's refreshed frequently, it could cause cascading latency.

The production fix: use IHttpClientFactory with typed clients to call each service. Register them in Program.cs with base addresses. The admin's JWT gets forwarded as a Bearer header on each call. A more advanced approach is CQRS with a read model — each service publishes events that Admin subscribes to, maintaining its own materialized view of aggregate stats. This avoids synchronous calls entirely.
Q2: Why is [Authorize(Roles = "Admin")] at the class level, not the method level? ▼
Security by default. If the authorization attribute is on each method, a developer adding a new endpoint to AdminController might forget to add the attribute — that endpoint would then be publicly accessible. In an admin-only service, that's a critical vulnerability.

Class-level authorization means every endpoint in the controller is Admin-only by default. If you specifically want to expose one endpoint publicly (unlikely for Admin), you explicitly add [AllowAnonymous] — requiring active effort to make something less secure rather than more secure. Always make the secure path the default path.
Q3: What would you add to Admin Service to make it production-grade? ▼
Four things: (1) Dashboard cross-service data — typed HttpClient factories calling Auth, Ledger, UserProfile with cached responses (5-minute Redis cache for aggregate stats). (2) FraudFlag resolution — a PATCH endpoint to mark flags as resolved with a resolution message. (3) Audit logging — every admin action (who flagged what, when, and why) written to a separate AuditLog table. (4) Role granularity — "Super Admin" vs "Support Agent" roles with different permission levels. Right now "Admin" is one undifferentiated role — a support agent and a super admin have identical access.

💥 The 502 Error Story (Interview Gold)

Root cause: google-generativeai package was installed alongside anthropic. It monkey-patched HTTP client configuration, routing requests to Gemini instead of Anthropic API. Gateway received the Gemini error — 502 Bad Gateway.

Fix: Clean venv + pip install anthropic==0.28.0 only. No other AI packages in the same environment.

Lesson: Always pin AI SDK versions. Never install competing AI provider SDKs in the same venv.

5 Interview Q&A — Chatbot

Q1: Why is the chatbot in Python instead of .NET? ▼
Two reasons. First, practical: the Anthropic Python SDK is the most mature and best-documented client. Python has the richest AI/ML ecosystem — langchain, embeddings, vector databases — all available if we want to extend the chatbot later. The .NET SDK exists but has less community support.

Second, architectural: microservices enable polyglot architecture — use the best tool for each domain. AI processing is Python's domain. Financial transaction processing is .NET's domain. As long as they communicate via HTTP, they never need to know what language the other is written in. This is the key microservices benefit: independent technology stacks per service.
Q2: The service is stateless — how does it maintain conversation context? ▼
The frontend manages state. Every request to POST /api/chat includes the complete conversation history as an array of {role, content} objects. The service appends the new user message, sends the full array to Claude, and returns the response. It stores nothing between requests.

This is correct design for a horizontally scalable service. If you have 3 chatbot instances behind a load balancer, any instance can handle any request from any user because the request is self-contained — it carries all the context needed. If state were in the service, you'd need sticky sessions or a shared session store like Redis.
Q3: What caused the 502 error and what does it tell you about dependency management? ▼
google-generativeai was installed alongside anthropic in the same virtual environment. The Google package patches Python's HTTP client configuration at import time — when Anthropic initialises its client, the endpoint routing was already corrupted, directing requests to Google's API instead. Google's API returned an error that Ocelot received and surfaced as 502.

The fix: delete the venv entirely and recreate it with only the required packages — no competing AI SDKs. The lesson: virtual environments provide isolation between projects but not between packages within the same project. Competing packages from the same domain (AI/ML providers) often conflict at the HTTP client level. Always pin versions in requirements.txt and audit dependencies before adding new ones to an existing environment.

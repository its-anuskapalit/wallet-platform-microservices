1 Service Context — System View

Exact Responsibility

Auth Service owns one job: prove who you are and issue a signed certificate (JWT) that every other service trusts. It never moves money, stores profiles, or sends emails. It only answers: "Is this person who they claim to be?"

Think of it as the passport office of the platform. It doesn't decide what you can do — it just issues your passport. Other services decide what the passport holder is allowed to do.

✅ Invariants It Must Always Maintain
  • Passwords are never stored in plain text — BCrypt at work factor 12
  • Refresh tokens are single-use only — old token revoked immediately on refresh
  • Role is always server-assigned — never from user input
  • Email is globally unique — enforced at DB + service layer
  • JWT secret never leaves server — signing is one-way
💥 What Breaks If Auth Goes Down
  • No new logins — existing valid JWTs still work (stateless)
  • No new registrations — UserProfile/Wallet not created for new users
  • Token refresh fails — users get logged out after 60 min
  • Gateway JWT validation still works (secret is in Gateway config too)

2 Clean Architecture Analysis

AuthService.Core/ ← Domain layer (pure C#, zero framework dependencies) Entities/ User.cs ← The real domain object RefreshToken.cs Interfaces/ IAuthService.cs ← Contract: what Auth can DO IAuthRepository.cs ← Contract: how Auth PERSISTS ITokenService.cs ← Contract: how tokens are GENERATED Services/ AuthService.cs ← Business logic lives here TokenService.cs ← JWT generation logic DTOs/ LoginRequestDto.cs RegisterRequestDto.cs AuthResponseDto.cs AuthService.Infrastructure/ ← Implementation layer (EF Core, SQL Server) Repositories/ AuthRepository.cs ← Implements IAuthRepository using EF Core Persistence/ AuthDbContext.cs ← EF Core context, table config AuthService.API/ ← Delivery layer (ASP.NET Core) Controllers/ AuthController.cs ← HTTP in → Service call → HTTP out Program.cs ← DI wiring, middleware, startup
Why Each Layer Exists

Core — Business rules are technology-agnostic. If you swap SQL Server for MongoDB tomorrow, zero Core code changes. The rule "passwords must be BCrypt hashed" lives in Core, not in a controller.

Infrastructure — EF Core is a detail. Core declares IAuthRepository. Infrastructure provides the concrete SQL implementation. Core doesn't know SQL exists.

API — ASP.NET is a delivery mechanism. The real work is in Core. The controller is just a translator: HTTP → domain call → HTTP.

What Breaks Without This Structure

If controller calls DbContext directly → you can't unit test it without a real DB. Every test needs SQL Server running.

If entity has controller logic → changing HTTP response format requires touching your domain model.

If business logic is in repository → your data access layer starts making business decisions — the classic "fat repository" anti-pattern.

Dependency Inversion in Action

// AuthService.cs (Core) — depends on abstraction, not concretion
public class AuthDomainService : IAuthService
{

    private readonly ITokenService   _tokens;  // ← interface, not TokenService

// Program.cs (API) — only place that binds interface → implementation
builder.Services.AddScoped<IAuthRepository, AuthRepository>();
builder.Services.AddScoped<IAuthService,    AuthDomainService>();
builder.Services.AddScoped<ITokenService,   TokenService>();

Why this matters for your tests: All 38 unit tests work because AuthService depends on IAuthRepository — not the real one. Tests pass Mock<IAuthRepository> and never touch SQL Server.

3 Deep File-by-File Code Review

📄 AuthController.cs — API Layer
[ApiController]
[Route("api/auth")]
public class AuthController : ControllerBase
{
    private readonly IAuthService _authService;

    public AuthController(IAuthService authService)  // ← DI, not new()
        => _authService = authService;

    [HttpPost("register")]
    public async Task<IActionResult> Register([FromBody] RegisterRequestDto dto)
    {
        // [ApiController] auto-validates data annotations — no if(!ModelState) needed
        var result = await _authService.RegisterAsync(dto);
        return result.IsSuccess
            ? CreatedAtAction(nameof(Register), result.Data)  // 201
            : Conflict(new { error = result.Error });          // 409
    }

    [Authorize]
    [HttpGet("me")]
    public IActionResult Me()
    {
        // Reads directly from JWT claims — no DB call needed
        return Ok(new {
            UserId   = User.FindFirst(ClaimTypes.NameIdentifier)?.Value,
            Email    = User.FindFirst(ClaimTypes.Email)?.Value,
            Role     = User.FindFirst(ClaimTypes.Role)?.Value,
            FullName = User.FindFirst("fullName")?.Value
        });
    }

    [Authorize(Roles = "Admin")]
    [HttpGet("admin-only")]
    public IActionResult AdminOnly() => Ok(new { message = "You are an admin." });
}

Why thin controllers? The controller has one job: translate HTTP into domain calls. It knows nothing about BCrypt, JWT, or SQL. If you need to add a gRPC endpoint tomorrow, you reuse IAuthService — the business logic is untouched.

Trade-off: /me reads from JWT claims without hitting DB. This means if a user is deactivated, their token is still valid for up to 60 minutes. A real-time check would require a DB call on every request — too expensive at scale.

📄 AuthService.cs — Core Domain Service
public async Task<Result<AuthResponseDto>> RegisterAsync(RegisterRequestDto dto)
{
    // 1. Check duplicate email — business rule
    if (await _users.ExistsByEmailAsync(dto.Email))
        return Result<AuthResponseDto>.Failure("Email already registered.");

    // 2. Create entity — password hashed HERE, not in repository
    var user = new User
    {
        Id           = Guid.NewGuid(),
        Email        = dto.Email.ToLower().Trim(),   // normalised
        PasswordHash = BCrypt.Net.BCrypt.HashPassword(dto.Password),
        FullName     = dto.FullName,
        Role         = "User",     // ← ALWAYS server-set, never from input
        IsActive     = true,
        CreatedAt    = DateTime.UtcNow
    };

    // 3. Persist
    await _users.CreateUserAsync(user);

    // 4. Generate tokens
    var accessToken  = _tokens.GenerateAccessToken(user);
    var refreshToken = _tokens.GenerateRefreshToken();
    await _users.AddRefreshTokenAsync(new RefreshToken {
        Token     = refreshToken,
        UserId    = user.Id,
        ExpiresAt = _tokens.GetRefreshTokenExpiry(),
        IsRevoked = false
    });

    // 5. Publish event AFTER persistence — user must exist before consumers reference it
    await _publisher.PublishAsync("user.exchange", "user.registered",
        new UserRegisteredEvent { UserId = user.Id, Email = user.Email });

    return Result<AuthResponseDto>.Success(BuildResponse(user, accessToken, refreshToken));
}

public async Task<Result<AuthResponseDto>> LoginAsync(LoginRequestDto dto)
{
    var user = await _users.GetByEmailAsync(dto.Email);

    // Intentionally same error for "not found" and "wrong password"
    // Prevents user enumeration attack
    if (user == null || !BCrypt.Net.BCrypt.Verify(dto.Password, user.PasswordHash))
        return Result<AuthResponseDto>.Failure("Invalid email or password.");

    if (!user.IsActive)
        return Result<AuthResponseDto>.Failure("Account is deactivated.");

    // ... generate + store refresh token, return tokens
}
Critical security detail: Login returns the same error for both "user not found" and "wrong password." If you said "Email not found" for missing users, attackers could enumerate which emails are registered. Same error = no information leakage.
📄 TokenService.cs — JWT Generation
public string GenerateAccessToken(User user)
{
    var key   = new SymmetricSecurityKey(Encoding.UTF8.GetBytes(_config["Jwt:Key"]!));
    var creds = new SigningCredentials(key, SecurityAlgorithms.HmacSha256);

    var claims = new[]
    {
        new Claim(JwtRegisteredClaimNames.Sub,   user.Id.ToString()),
        new Claim(JwtRegisteredClaimNames.Email, user.Email),
        new Claim(JwtRegisteredClaimNames.Jti,   Guid.NewGuid().ToString()),  // unique token ID
        new Claim(ClaimTypes.Role,               user.Role),
        new Claim("fullName",                    user.FullName)
    };

    var token = new JwtSecurityToken(
        issuer:             _config["Jwt:Issuer"],    // WalletPlatform
        audience:           _config["Jwt:Audience"],  // WalletPlatform.Clients
        claims:             claims,
        expires:            DateTime.UtcNow.AddMinutes(60),
        signingCredentials: creds);

    return new JwtSecurityTokenHandler().WriteToken(token);
}

// Refresh token = 64 cryptographically random bytes → base64 string
// NOT a JWT — just an opaque random secret stored in DB
public string GenerateRefreshToken()
    => Convert.ToBase64String(RandomNumberGenerator.GetBytes(64));

Why is the refresh token NOT a JWT? A JWT is self-contained and can't be revoked without a blacklist. The refresh token is stored in DB, so revocation is just marking IsRevoked = true. Simple, reliable, database-backed revocation.

Why jti claim? Each JWT gets a unique ID. In a production system with a token blacklist (Redis), you'd blacklist the jti on logout — allowing near-instant JWT invalidation without full statefulness.

📄 AuthRepository.cs — Infrastructure Layer
public class AuthRepository : IAuthRepository
{
    private readonly AuthDbContext _ctx;

    // EmailExists — for duplicate check during register
    public async Task<bool> ExistsByEmailAsync(string email)
        => await _ctx.Users
            .AsNoTracking()                    // ← read-only, no change tracking overhead
            .AnyAsync(u => u.Email == email.ToLower().Trim());

    // GetByEmail — for login (needs full entity)
    public async Task<User?> GetByEmailAsync(string email)
        => await _ctx.Users
            .AsNoTracking()
            .FirstOrDefaultAsync(u => u.Email == email.ToLower().Trim());

    // GetRefreshToken — for refresh/revoke (needs tracking to update IsRevoked)
    public async Task<RefreshToken?> GetRefreshTokenAsync(string token)
        => await _ctx.RefreshTokens
            .Include(rt => rt.User)   // ← loads User navigation property
            .FirstOrDefaultAsync(rt => rt.Token == token && !rt.IsRevoked);
}

AsNoTracking() strategy: Used for all reads where you don't intend to update. EF Core won't create a snapshot of the entity for change detection. For a high-read service like Auth, this is a meaningful performance gain — especially under load.

GetRefreshToken uses tracking (no AsNoTracking): Because immediately after loading it, the service calls IsRevoked = true and SaveChangesAsync(). EF's change tracker detects the modification and issues an UPDATE automatically.

📄 User.cs + RefreshToken.cs — Domain Entities
// Users table — two tables, clear responsibilities
public class User : BaseEntity
{
    public Guid   Id           { get; set; }
    public string Email        { get; set; } = string.Empty;  // UNIQUE index in DB
    public string PasswordHash { get; set; } = string.Empty;  // BCrypt, never plain
    public string FullName     { get; set; } = string.Empty;
    public string Phone        { get; set; } = string.Empty;
    public string Role         { get; set; } = "User";        // "User" | "Admin"
    public bool   IsActive     { get; set; } = true;
    public DateTime CreatedAt  { get; set; }

    // Navigation property — EF loads related refresh tokens when needed
    public ICollection<RefreshToken> RefreshTokens { get; set; } = new List<RefreshToken>();
}

public class RefreshToken : BaseEntity
{
    public Guid     Id             { get; set; }
    public string   Token          { get; set; } = string.Empty;  // UNIQUE index
    public DateTime ExpiresAt      { get; set; }
    public bool     IsRevoked      { get; set; } = false;
    public string?  ReplacedByToken { get; set; }   // audit trail: what replaced this token
    public Guid     UserId         { get; set; }    // FK
    public User     User           { get; set; } = null!;
}

ReplacedByToken field: When a refresh token is rotated, you store the token that replaced it. This enables an audit trail — if a stolen token is used, you can trace the full token chain and detect the breach.

📄 AuthDbContext.cs — Persistence Configuration
public class AuthDbContext : DbContext
{
    public DbSet<User>         Users         { get; set; }
    public DbSet<RefreshToken> RefreshTokens { get; set; }

    protected override void OnModelCreating(ModelBuilder mb)
    {
        // Unique constraint — enforced at DB level, not just service level
        mb.Entity<User>()
          .HasIndex(u => u.Email)
          .IsUnique();

        mb.Entity<RefreshToken>()
          .HasIndex(rt => rt.Token)
          .IsUnique();

        // Cascade delete — when user deleted, their refresh tokens go too
        mb.Entity<RefreshToken>()
          .HasOne(rt => rt.User)
          .WithMany(u => u.RefreshTokens)
          .HasForeignKey(rt => rt.UserId)
          .OnDelete(DeleteBehavior.Cascade);
    }
}
Defense in depth: The unique email index exists at both the service layer (ExistsByEmailAsync check) AND the database level (HasIndex.IsUnique). If two concurrent register requests pass the service check simultaneously, the DB constraint catches it. This is essential — never rely on service-layer checks alone for uniqueness.

4 Execution Trace — Login Flow

Scenario: POST /gateway/auth/login → { email, password }
1
Ocelot Gateway (5000) receives the request. Checks JWT middleware — login is [AllowAnonymous], so no auth check. Route rule matches /gateway/auth/** → forwards to http://localhost:5001/api/auth/login
2
AuthController.Login() — [ApiController] validates model binding. [Required] and [EmailAddress] data annotations checked. If invalid → 400 returned before controller method even executes.
3
AuthService.LoginAsync() — calls _users.GetByEmailAsync(dto.Email). EF issues: SELECT TOP 1 * FROM Users WHERE Email = 'x@y.com'
4
Password verification — BCrypt.Verify(dto.Password, user.PasswordHash). BCrypt re-hashes the input with the stored salt and compares. This takes ~200ms intentionally — it's the work factor 12 cost that makes brute force expensive.
5
Token generation — TokenService.GenerateAccessToken(user) builds JWT with claims (sub, email, role, fullName, jti). Signs with HMACSHA256. GenerateRefreshToken() produces 64 random bytes → base64.
6
Refresh token stored — INSERT INTO RefreshTokens with IsRevoked=false, ExpiresAt = Now+7days.
7
200 OK returned — { userId, email, accessToken, refreshToken, accessTokenExpiry }

5 Distributed Systems Concerns

Idempotency

Register: Not idempotent by design — sending the same email twice returns 409 on the second call. The unique index guarantees this even under concurrent requests.

Login: Naturally idempotent — calling it N times creates N refresh tokens, but all are valid. Old ones expire after 7 days.

Gap: No explicit idempotency key on register. A network retry after a successful register (client didn't get response) would return 409. This is acceptable UX — tell the user to login instead.

Consistency Model

Auth DB: Strong consistency — all writes go to a single SQL Server. ACID guarantees apply.

Cross-service: Eventual consistency — the UserRegisteredEvent may reach UserProfile/Wallet seconds after Auth responds 200. During that window the user exists in AuthDb but not in UserProfileDb.

Risk: If RabbitMQ is down, the event is lost and downstream services never create the user's profile/wallet. The user can login but can't do anything. Mitigation: Outbox pattern (not implemented — noted gap).

Refresh Token Rotation — The Revocation Chain
// RefreshAsync — token rotation logic
var existing = await _users.GetRefreshTokenAsync(token);

if (existing == null || existing.IsRevoked || existing.ExpiresAt < DateTime.UtcNow)
    return Result.Failure("Invalid or expired refresh token.");

// Generate new pair
var newAccess  = _tokens.GenerateAccessToken(existing.User);
var newRefresh = _tokens.GenerateRefreshToken();

// Revoke old — set IsRevoked=true, store what replaced it (audit trail)
existing.IsRevoked      = true;
existing.ReplacedByToken = newRefresh;

// Store new refresh token
await _users.AddRefreshTokenAsync(new RefreshToken { Token = newRefresh, ... });
await _ctx.SaveChangesAsync();  // ← single transaction: revoke + create atomically
Reuse detection: If an attacker steals and uses a refresh token before the legitimate user does, the legitimate user's next refresh call will get 401 (token already revoked). This is a signal of token theft. In production: revoke ALL tokens for this user and force re-login.

6 Performance & Scalability

⚠️ Bottlenecks
  • BCrypt at work factor 12 — intentionally slow (~200ms). Login is CPU-bound. Under heavy load, this limits login throughput. Mitigation: horizontal scaling (multiple Auth service instances).
  • Email uniqueness check — requires a DB read on every register. Index on Email makes it O(log n) but still a network round trip.
  • RefreshTokens table growth — tokens accumulate over 7 days. Need a background cleanup job to delete expired/revoked tokens.
📈 Scaling Strategy
  • JWT is stateless — gateway validates token signature without calling Auth service. Auth doesn't get hit on every API call, only on login/refresh.
  • Horizontal scaling — Auth service can run N replicas. No local state. DB is the only shared state.
  • Caching opportunity: User lookup by email could be Redis-cached. But cache invalidation is tricky if user is deactivated.

8 Design Trade-offs

Why Microservice for Auth, Not Monolith?

Independent deployability: You can update the refresh token rotation logic or change JWT expiry without touching Wallet or Ledger. In a monolith, any deploy risks breaking everything.

Security isolation: JWT secrets and password hashes are in a separate process with its own DB. If the Catalog service is compromised, attackers don't get access to the AuthDb.

Cost: Each service call now crosses a network boundary. Register triggers RabbitMQ + 3 downstream consumers. In a monolith this would be 3 in-process method calls.

Database-per-service Trade-off

Benefit: Auth's schema can evolve independently. You can add columns to Users without coordination with other teams.

Cost: No cross-service JOIN. If Admin service needs user email + wallet balance, it must call two services, not one SELECT JOIN.

Event-driven Registration Trade-off

Benefit: Auth doesn't wait for UserProfile/Wallet to be created. Register returns in ~300ms regardless of downstream load.

Cost: If RabbitMQ drops the event, user has no wallet. No outbox pattern = no delivery guarantee. This is the most significant reliability gap in Auth.

10 Interview-Level Q&A

Q1: Why can't you immediately invalidate a JWT after logout? How would you fix it? ▼
JWTs are stateless and self-validating. The gateway validates the signature locally — it doesn't call Auth service. So even if you mark the token as "logged out" in your DB, the gateway never checks that. The token is valid until it expires.

Fix: Store revoked JTIs in Redis with TTL equal to token expiry. On every request, gateway checks Redis: "is this jti blacklisted?" If yes → 401. This adds one Redis read per request — but Redis is in-memory so it's microseconds, not milliseconds. The jti claim is already in every JWT in this service — the infrastructure is ready.
Q2: What is refresh token rotation and why does it improve security? ▼
Refresh token rotation means each time you use a refresh token, it's immediately invalidated and replaced with a new one. The old token's IsRevoked is set to true in the DB.

Security gain: If an attacker steals your refresh token and uses it before you do, your next refresh attempt will fail (token already revoked). This is a signal of token theft. Without rotation, a stolen refresh token is valid for 7 days — the attacker can silently renew access indefinitely.
Q3: Why return the same error for "email not found" and "wrong password"? ▼
This prevents user enumeration. If login returned "Email not registered" for unknown emails, an attacker could iterate through a list of emails and discover which ones have accounts — then target those accounts specifically or sell the list. By returning "Invalid email or password" for both cases, the attacker learns nothing about whether the email exists.
Q4: How does Clean Architecture make this service testable? ▼
AuthService.cs (Core) depends on IAuthRepository, not AuthRepository. In unit tests, you pass Mock<IAuthRepository> that returns controlled data without touching SQL Server. All 38 tests run in milliseconds with no infrastructure dependencies. The interface is the seam that makes testing possible. Without it, every test would need a running database.
Q5: What is the biggest reliability risk in Auth and how would you fix it? ▼
The event publish happens after the DB write, but there's no transactional guarantee between them. If RabbitMQ is down or the publish fails, the user is created in AuthDb but UserProfile/Wallet never get the event — the user exists but can't use the platform.

Fix: Outbox Pattern. Instead of publishing to RabbitMQ directly, write the event to an OutboxEvents table in the same DB transaction as the user INSERT. A background job polls the outbox table and publishes to RabbitMQ, marking events as published. Now the event is guaranteed to be delivered eventually — even if RabbitMQ was down during registration.

11 30-Second & 2-Minute Explanation

⚡ 30-Second Answer

Auth Service is the identity anchor of the platform. It owns user registration, login, and JWT issuance. It uses BCrypt at work factor 12 for password hashing, issues 60-minute JWTs with claims baked in, and manages refresh token rotation with revocation. It publishes a UserRegisteredEvent to RabbitMQ so downstream services (Wallet, UserProfile, Notifications) can set up the user asynchronously. Every other service trusts the JWT — they validate the signature without calling Auth.

🎯 2-Minute Deep Dive Answer

Auth Service follows Clean Architecture: Core holds domain logic and interfaces, Infrastructure implements EF Core repositories, and the API layer is a thin controller that maps HTTP to domain calls. This separation is what makes 38 unit tests possible — the core service has zero framework dependencies.

The JWT is stateless — the gateway validates the HMACSHA256 signature locally on every request without calling Auth. This means Auth isn't hit on every API call, only on login and refresh. The trade-off is that a revoked access token remains valid for up to 60 minutes — solvable with a Redis-backed jti blacklist.

Refresh tokens are single-use and database-backed — not JWTs — so they can be revoked instantly. Rotation means every use of a refresh token invalidates it and creates a new one. If a stolen token is used before the legitimate user, the legitimate user detects it on their next refresh attempt.

The main reliability gap is the UserRegisteredEvent publish. There's no transactional guarantee between the DB write and the RabbitMQ publish. In production I'd add the Outbox Pattern — write the event to the same database transaction, and have a background job guarantee delivery.

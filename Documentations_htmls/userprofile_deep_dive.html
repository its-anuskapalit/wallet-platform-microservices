1 Service Context — System View

Exact Responsibility

Auth says "you exist and here's your token." UserProfile says "here's who you are." It owns all identity data beyond credentials — name, address, date of birth, and critically, the KYC (Know Your Customer) lifecycle.

In fintech, KYC is a legal and regulatory requirement. A user cannot move money until their identity is verified by a human admin. UserProfile owns this entire workflow: document submission → admin review → approval/rejection → event notification.

✅ Invariants It Must Always Maintain
  • Every user has exactly one profile — no duplicates (idempotent consumer)
  • KycStatus starts as Pending — always, no exceptions
  • Only Admin can change KycStatus — user can never self-approve
  • Profile is created event-driven — never by user's first API call
  • UserId in all operations always comes from JWT, never from request body
💥 What Breaks If UserProfile Goes Down
  • New users register fine — Auth is independent
  • Profile auto-creation fails — UserRegistered events queue up in RabbitMQ
  • KYC submission blocked — users can't progress to Approved
  • Wallet operations not directly blocked — Wallet checks KYC by calling its own DB (or gateway)
  • Events replay when service recovers (RabbitMQ queues persist)

Why Two Services in Core (ProfileService + KycService)?

Profile management (name, address) and KYC workflow (document review, status transitions, event publishing) are two different bounded contexts that happen to share a database. Splitting them into two services keeps each class small and focused. Single Responsibility at the service level.

Trade-off: Two service interfaces injected into two controllers. Slightly more DI wiring, but each service is independently testable and understandable.

Why Consumer Lives in Infrastructure?

The UserRegisteredConsumer is an infrastructure detail — it depends on RabbitMQ, which is an external technology. Core defines the IProfileRepository interface. Infrastructure provides both the EF implementation AND the RabbitMQ consumer that uses it.

Core never knows RabbitMQ exists. If you replaced RabbitMQ with Azure Service Bus, only Infrastructure changes.

3 Deep File-by-File Code Review

📄 UserRegisteredConsumer.cs — The Most Important File in This Service
public class UserRegisteredConsumer : BaseConsumer<UserRegisteredEvent>
{
    private readonly IServiceScopeFactory _scopeFactory;

    // Queue binding — this is how the consumer knows WHERE to listen
    protected override string QueueName    => "userprofile.user.queue";
    protected override string ExchangeName => "user.exchange";
    protected override string RoutingKey   => "user.registered";

    protected override async Task HandleAsync(UserRegisteredEvent message, CancellationToken ct)
    {
        // CRITICAL: IServiceScopeFactory — not constructor injection
        // BaseConsumer is a Singleton (long-lived)
        // EF Core DbContext is Scoped (per-request)
        // You CANNOT inject Scoped into Singleton directly — it causes scope violation
        // Solution: create a new scope manually per message
        using var scope = _scopeFactory.CreateScope();
        var repo = scope.ServiceProvider.GetRequiredService<IProfileRepository>();

        // IDEMPOTENCY CHECK — most critical line in the consumer
        // RabbitMQ can deliver the same message more than once (at-least-once delivery)
        // Without this check, one user could get duplicate profile rows
        if (await repo.ExistsByUserIdAsync(message.UserId))
            return;  // already processed, BasicAck will still be sent by BaseConsumer

        await repo.AddAsync(new UserProfile
        {
            UserId    = message.UserId,
            Email     = message.Email,
            FullName  = message.FullName,
            Phone     = message.Phone,
            KycStatus = KycStatus.Pending  // ALWAYS Pending — never set by user
        });

        await repo.SaveChangesAsync();
        // BaseConsumer calls BasicAck() after HandleAsync returns successfully
        // If HandleAsync throws, BaseConsumer calls BasicNack(requeue: true)
    }
}
The IServiceScopeFactory pattern is critical to understand. BaseConsumer is registered as a Singleton because it holds a long-lived RabbitMQ connection. EF Core's DbContext is Scoped — it lives only for a single request. If you inject DbContext directly into the Singleton, the Scoped service gets "captured" and lives as long as the Singleton — it never gets disposed. This causes memory leaks and stale data. The fix: create a fresh scope per message and resolve DbContext from it.
📄 ProfileService.cs — Get & Update Logic
public async Task<Result<ProfileDto>> GetByUserIdAsync(Guid userId)
{
    var profile = await _profiles.GetByUserIdAsync(userId);
    if (profile is null)
        return Result<ProfileDto>.Failure("Profile not found.");

    return Result<ProfileDto>.Success(MapToDto(profile));
}

public async Task<Result<ProfileDto>> UpdateProfileAsync(Guid userId, UpdateProfileDto dto)
{
    var profile = await _profiles.GetByUserIdAsync(userId);
    if (profile is null)
        return Result<ProfileDto>.Failure("Profile not found.");

    // PATCH semantics — only update fields that were provided
    // If client sends null for a field, we DON'T overwrite with null
    if (!string.IsNullOrWhiteSpace(dto.Phone))       profile.Phone       = dto.Phone;
    if (!string.IsNullOrWhiteSpace(dto.Address))     profile.Address     = dto.Address;
    if (!string.IsNullOrWhiteSpace(dto.DateOfBirth)) profile.DateOfBirth = dto.DateOfBirth;
    if (!string.IsNullOrWhiteSpace(dto.FullName))    profile.FullName    = dto.FullName;
    profile.UpdatedAt = DateTime.UtcNow;

    // EF change tracking detects modified properties — no explicit UPDATE needed
    await _profiles.SaveChangesAsync();
    return Result<ProfileDto>.Success(MapToDto(profile));
}

// Entity → DTO mapping — strips internal fields, exposes only safe data
private static ProfileDto MapToDto(UserProfile p) => new()
{
    UserId     = p.UserId,
    Email      = p.Email,
    FullName   = p.FullName,
    Phone      = p.Phone,
    Address    = p.Address,
    KycStatus  = p.KycDocument?.Status  // null-safe: Pending profiles have no document yet
};

Patch semantics vs PUT: A true HTTP PUT would replace the entire resource. Here we behave more like PATCH — only update fields that were actually sent. This is safer UX (user can update just their phone without sending all other fields) but slightly misuses the PUT verb. A strict REST API would use PATCH for this.

📄 KycService.cs — KYC Business Logic
public async Task<Result<string>> SubmitKycAsync(Guid userId, KycSubmitDto dto)
{
    var profile = await _profiles.GetByUserIdAsync(userId);
    if (profile is null)
        return Result<string>.Failure("Profile not found.");

    // Guard: only one KYC document per user at a time
    if (profile.KycDocument is not null)
        return Result<string>.Failure("KYC already submitted.");

    var doc = new KycDocument
    {
        UserProfileId  = profile.Id,   // FK to UserProfiles, not UserId directly
        DocumentType   = dto.DocumentType,    // "Aadhaar", "PAN", "Passport"
        DocumentNumber = dto.DocumentNumber,
        Status         = KycStatus.Pending    // always starts Pending
    };

    await _kyc.AddAsync(doc);
    await _kyc.SaveChangesAsync();
    return Result<string>.Success("KYC submitted successfully. Pending review.");
}

public async Task<Result<string>> ReviewKycAsync(Guid userId, KycReviewDto dto, string reviewedBy)
{
    var profile = await _profiles.GetByUserIdAsync(userId);
    if (profile is null) return Result<string>.Failure("Profile not found.");

    // State machine guard — can only review Submitted documents
    if (profile.KycDocument is null)
        return Result<string>.Failure("No KYC document submitted.");

    if (profile.KycDocument.Status == KycStatus.Approved)
        return Result<string>.Failure("KYC already approved.");

    // Atomic update — both profile status + document status change together
    profile.KycStatus             = dto.Status;   // Approved or Rejected
    profile.KycDocument.Status    = dto.Status;
    profile.KycDocument.ReviewedBy = reviewedBy;  // audit trail — who approved it

    await _profiles.SaveChangesAsync();  // one SaveChanges covers both entities (EF tracks both)

    // Publish event AFTER save — notification sent only if DB committed
    await _publisher.PublishAsync("user.exchange", "kyc.status.updated",
        new KycStatusUpdatedEvent {
            UserId    = userId,
            Status    = dto.Status.ToString(),
            Remarks   = dto.Remarks,
            Timestamp = DateTime.UtcNow
        });

    return Result<string>.Success($"KYC {dto.Status} successfully.");
}
Atomic update across two entities: When an admin approves KYC, both UserProfile.KycStatus and KycDocument.Status must change together. Because EF Core's change tracker tracks both objects within the same DbContext scope, a single SaveChangesAsync() wraps both updates in one database transaction. They either both commit or both roll back.
📄 ProfileRepository.cs — Key Query Pattern
public async Task<UserProfile?> GetByUserIdAsync(Guid userId) =>
    await _db.UserProfiles
        .Include(p => p.KycDocument)   // ← EAGER loading — always loads document with profile
        .FirstOrDefaultAsync(p => p.UserId == userId);

public async Task<bool> ExistsByUserIdAsync(Guid userId) =>
    await _db.UserProfiles
        .AnyAsync(p => p.UserId == userId);  // ← no AsNoTracking needed — AnyAsync never tracks

Why .Include(p => p.KycDocument) everywhere? The KYC status is displayed on every profile GET. Without Include, p.KycDocument would be null even if a document exists (EF doesn't load navigation properties by default — it's called lazy loading and is disabled in EF Core by default). Eager loading with Include ensures one SQL JOIN instead of two separate queries.

Trade-off: Even for a simple "does this profile exist?" check, you could accidentally use GetByUserIdAsync which also loads the KycDocument. The ExistsByUserIdAsync method exists precisely to avoid this — it compiles to SELECT CASE WHEN EXISTS(...) with no JOIN, far cheaper.

📄 Entities — Domain Modeling Decisions
public class UserProfile : BaseEntity
{
    public Guid    UserId    { get; set; }   // ← NOT a real FK — AuthDb is a different DB
    public string  Email     { get; set; } = string.Empty;
    public string? FullName  { get; set; }  // nullable — filled later by user
    public string? Phone     { get; set; }
    public string? Address   { get; set; }
    public string? DateOfBirth { get; set; }
    public KycStatus KycStatus { get; set; } = KycStatus.Pending;

    // Navigation property — one-to-one with KycDocument
    public KycDocument? KycDocument { get; set; }
}

public class KycDocument : BaseEntity
{
    public Guid      UserProfileId  { get; set; }  // FK to UserProfiles.Id (same DB)
    public string    DocumentType   { get; set; } = string.Empty;
    public string    DocumentNumber { get; set; } = string.Empty;
    public KycStatus Status         { get; set; } = KycStatus.Pending;
    public string?   ReviewedBy     { get; set; }  // admin email — audit trail
    public DateTime  SubmittedAt    { get; set; }

    public UserProfile UserProfile  { get; set; } = null!;  // back-reference
}

public enum KycStatus { Pending, Submitted, Approved, Rejected }

Why is UserId not a real FK? UserProfile.UserId is a Guid that logically references AuthDb.Users.Id, but there is no database-level foreign key constraint between them — they're in different databases. This is the database-per-service trade-off: you lose referential integrity across service boundaries. The application layer must maintain this consistency through events and validation.

[ApiController]
[Route("api/kyc")]
public class KycController : ControllerBase
{
    [Authorize]                          // any authenticated user
    [HttpPost("submit")]
    public async Task<IActionResult> Submit([FromBody] KycSubmitDto dto) { ... }

    [Authorize(Roles = "Admin")]         // ← ONLY Admin role — enforced by ASP.NET Core policy
    [HttpPut("review/{userId}")]
    public async Task<IActionResult> Review(Guid userId, [FromBody] KycReviewDto dto)
    {
        var reviewedBy = User.FindFirstValue(ClaimTypes.Email)!;  // who clicked Approve
        var result = await _kycService.ReviewKycAsync(userId, dto, reviewedBy);

}
Security pattern — userId from JWT, not URL: For GET /me and PUT /me, the userId comes from the JWT claim, not the URL. This means a user cannot request /profile/other-user-id. They can only ever operate on their own profile. The Admin review endpoint accepts a userId in the URL because admins need to review specific users — but that endpoint requires the Admin role.
📄 UserProfileDbContext.cs — Schema Configuration
protected override void OnModelCreating(ModelBuilder mb)
{
    // One-to-one: each profile has at most one KYC document
    mb.Entity<UserProfile>()
      .HasOne(p => p.KycDocument)
      .WithOne(d => d.UserProfile)
      .HasForeignKey<KycDocument>(d => d.UserProfileId)
      .OnDelete(DeleteBehavior.Cascade);  // delete profile → delete document too

    // Unique constraint on UserId — enforced at DB level
    mb.Entity<UserProfile>()
      .HasIndex(p => p.UserId)
      .IsUnique();

    // Store enum as string — readable in DB, not magic numbers
    mb.Entity<UserProfile>()
      .Property(p => p.KycStatus)
      .HasConversion<string>();

    mb.Entity<KycDocument>()
      .Property(d => d.Status)
      .HasConversion<string>();
}

Why store enum as string? Without HasConversion<string>(), EF stores the enum as an integer (0, 1, 2, 3). If you look at the DB directly you see "0" instead of "Pending". String storage makes the DB human-readable and survives reordering of enum values without corrupt data.

Idempotency in the Consumer

RabbitMQ guarantees at-least-once delivery — the same message may arrive multiple times (network hiccup, service restart). The consumer handles this with a check:

if (await repo.ExistsByUserIdAsync(message.UserId))
    return;  // already processed — skip

This makes the consumer idempotent — processing the same event 10 times produces the same result as processing it once. The unique index on UserId in the DB also provides a second layer of defence.

Eventual Consistency Window

When a user registers in Auth, their profile in UserProfileDb is created milliseconds later via RabbitMQ — not atomically. During that window:

  • Auth returns 200 (user exists in AuthDb)
  • Profile doesn't exist in UserProfileDb yet
  • If user calls GET /profile/me immediately → 404

This is acceptable for a non-critical read. The window is typically <100ms. The real problem is if RabbitMQ drops the event entirely — then the profile is never created.

The Outbox Pattern Gap

In ReviewKycAsync(), the flow is:

await _profiles.SaveChangesAsync();   // ← DB committed here
await _publisher.PublishAsync(...);   // ← RabbitMQ publish here
// If RabbitMQ is down or publish throws after DB commit:
// → Status is Approved in DB
// → Notification email NEVER sent
// → User is approved but doesn't know it
Fix — Outbox Pattern: Write the KycStatusUpdatedEvent to an OutboxEvents table in the same DB transaction as the KYC update. A background job polls the outbox and publishes to RabbitMQ. This guarantees exactly-once delivery. Not implemented in this project — but this is the production-grade answer.

6 Performance & Scalability

⚠️ Bottlenecks
  • Eager loading KycDocument on every profile query — even for exists checks. The ExistsByUserIdAsync method exists to avoid this but all other reads always JOIN.
  • N+1 risk if listing profiles — no list endpoint now, but if added without Include, EF would query KycDocument for each profile separately.
  • No caching on profile reads — GET /me hits DB on every call. Profile data rarely changes — Redis with a 5-minute TTL would dramatically reduce DB load.
📈 Scaling Considerations
  • Horizontal scaling works cleanly — no local state, all state in SQL Server
  • Consumer concurrency — if multiple UserProfile instances run, multiple consumers may try to create the same profile simultaneously. The unique index on UserId + the idempotency check handle this race condition.
  • KYC is admin-driven and low volume — not a scaling concern in practice

8 Design Trade-offs

Why Event-Driven Profile Creation Instead of API Call?

Option A (what you built): Auth publishes UserRegisteredEvent → UserProfile consumer creates profile asynchronously.

Option B: After register, Auth calls POST /profile/create synchronously.

Why A wins: Option B creates a synchronous coupling — Auth's register endpoint is now only as fast and reliable as UserProfile service. If UserProfile is slow or down, registration fails or is slow. With event-driven, registration always returns fast. UserProfile catches up when it can. Loose coupling at the cost of eventual consistency.

One DB for Profile + KYC vs Two DBs

What you built: Both UserProfiles and KycDocuments are in the same UserProfileDb, owned by the same service.

Why correct: Profile and KYC are tightly coupled — you almost always need both together. Same service, same DB = single transaction for atomic updates. If they were in separate databases (separate services), you'd need a distributed transaction (2-phase commit) to update both atomically. Not worth the complexity.

Cross-DB Relationship (No Real FK)

UserProfile.UserId references AuthDb.Users.Id logically but there's no DB-level FK constraint. This means you could have orphaned profiles if a user is deleted from AuthDb without the event reaching UserProfileDb.

This is the fundamental trade-off of database-per-service: you trade referential integrity for service autonomy. The application logic (event-driven creation + existence checks) must substitute for what the DB would normally guarantee.

10 Interview-Level Q&A

Q1: Why do you use IServiceScopeFactory in the consumer instead of constructor injection for the repository? ▼
BaseConsumer is registered as a Singleton because it holds a long-lived RabbitMQ channel connection. EF Core's DbContext is registered as Scoped — meaning it's created per HTTP request and disposed after. If you inject a Scoped service into a Singleton, the Scoped service gets "captured" — it lives as long as the Singleton and never gets disposed. This is called a captive dependency and causes memory leaks and stale EF tracking state.

The fix: inject IServiceScopeFactory (which is itself Singleton-safe), and inside HandleAsync, create a new scope with CreateScope(). This gives you a fresh DbContext per message — same lifetime as if it were a real HTTP request. Dispose the scope when done.
Q2: How do you prevent duplicate profile creation if the UserRegisteredEvent is delivered twice? ▼
Two layers of defence. First, the application check: if (await repo.ExistsByUserIdAsync(message.UserId)) return; — if the profile already exists, skip processing and BasicAck the message (it was already handled).

Second, the database unique index on UserId. Even if two concurrent instances of the consumer pass the application check simultaneously (race condition), only one INSERT will succeed. The other will throw a unique constraint violation, which causes BaseConsumer to Nack and retry — and on retry, the application check catches it. Defense in depth: application layer + database layer.
Q3: How does EF Core update both UserProfile and KycDocument atomically in one call? ▼
EF Core's DbContext maintains a change tracker. When you load a UserProfile with .Include(p => p.KycDocument), both the profile and its document are tracked within the same DbContext instance. When you modify properties on both objects, the change tracker marks both as modified. When SaveChangesAsync() is called, EF wraps all pending changes — including both UPDATE statements — in a single database transaction. Either both commit or both roll back. You never have to manually open a SqlTransaction.
Q4: Why is the KYC state machine important in a fintech context? ▼
KYC (Know Your Customer) is a regulatory requirement — financial institutions are legally required to verify customer identity before allowing money movement. The state machine enforces the legal workflow: Pending (registered but unverified) → Submitted (documents provided) → Approved (verified, full access) / Rejected (failed, must resubmit).

The guards on state transitions (can't review what hasn't been submitted, can't re-approve already approved) prevent both user errors and potential manipulation. In production, KYC approval would also trigger a JWT refresh so the new status propagates immediately to the access token.
Q5: There's no real FK between UserProfile.UserId and AuthDb — how do you maintain consistency? ▼
This is the fundamental database-per-service trade-off. Without cross-DB FK constraints, consistency is maintained through: (1) Event-driven creation — profile is only created when UserRegisteredEvent is received, meaning the user must exist in AuthDb for the event to have been published. (2) Application-level validation — every operation checks that the profile exists before proceeding. (3) No delete operation — we never delete users, so there's no orphan problem.

The gap: if Auth deletes a user (not implemented), we'd need a UserDeletedEvent that triggers profile deletion. This is the compensation pattern for cross-service consistency.

11 30-Second & 2-Minute Explanation

⚡ 30-Second Answer

UserProfile Service owns user identity data and the KYC workflow. It's event-driven at its core — a UserRegisteredConsumer auto-creates a profile row when Auth publishes the UserRegistered event, so users never need to explicitly create their profile. The KYC state machine moves through Pending → Submitted → Approved/Rejected. Only Admins can change KycStatus. On approval, a KycStatusUpdatedEvent fires so Notification sends an email. The tricky engineering detail is that the consumer uses IServiceScopeFactory to avoid injecting a Scoped DbContext into a Singleton consumer.

🎯 2-Minute Deep Dive

UserProfile Service has two main concerns: profile management and KYC workflow. These are split into two services (ProfileService and KycService) within the same bounded context, keeping each class focused on one thing.

The most architecturally interesting part is the UserRegisteredConsumer. It inherits from BaseConsumer<T>, which handles the RabbitMQ connection, acknowledgements, and dead-letter routing. The consumer creates a profile automatically when Auth publishes UserRegisteredEvent — the user never needs to call a "create profile" endpoint. Making the consumer idempotent is critical because RabbitMQ guarantees at-least-once delivery. The application check plus the database unique index form two layers of duplicate protection.

For KYC, when an admin approves, EF Core updates both UserProfile.KycStatus and KycDocument.Status in a single database transaction — the change tracker handles this automatically since both entities are loaded within the same DbContext scope. The KycStatusUpdatedEvent is then published so the user gets notified by email.

The main production gap is the Outbox Pattern. If RabbitMQ goes down after the DB save but before the event publish, the user's KYC is approved but they never get the email. The fix is to write the event into an OutboxEvents table in the same transaction, with a background job guaranteeing delivery to RabbitMQ independently.
